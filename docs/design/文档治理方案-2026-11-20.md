## 2. 权威顺序（修订 AGENTS.md 一处）

在现有第 1、2 层之间插入验证地图，并按「回答什么问题」区分它和 ADR：

1. 代码与测试
2. 生成物：`docs/reference/facts.md`、`docs/INDEX.md`、AGENTS 现状块
3. **验证地图** `.agents/skills/verify-book-corpus/features/*.md`：产品**现在做什么**、怎么证明
4. `docs/adr/` 里 accepted 的决定：**为什么**这样做
5. 活文档正文：README、CONTRIBUTING、AGENTS、GLOSSARY、`apps/*/README.md`、`docs/检索/README.md`
6. `docs/design/`、`docs/briefs/`（按状态头读）
7. 记录：复盘、`reports/`、`artifacts/verify/`、踩坑账

活文档描述的用户可见行为和验证地图冲突时，改活文档。验证地图自己也会过期（D3），所以它同样要带 `失效源：`（见 §5 G3）。

## 3. 文档分类与职责

每份 md 只属于一类。类别决定谁能改、怎么退役、由哪道门禁看。

| 类 | 文件 | 只回答 | 改的规则 | 退役方式 | 门禁 |
|---|---|---|---|---|---|
| 入口 | `README.md` | 新克隆的人怎么从零装好、跑起来 | 随代码同提交改 | 不退役 | paths / cli / ports / 退役词 / 失效源 |
| 开发 | `CONTRIBUTING.md` | 改代码的流程、lint、提交 | 同上 | 不退役 | 同上 |
| Agent 规则 | `AGENTS.md`、`docs/agents/*` | 本机实例、写入纪律、权威顺序 | 同上；数字只进生成块 | 不退役 | 同上 + numbers |
| 应用手册 | `apps/*/README.md` | 这个服务的参数、环境变量、接口表 | 随 `apps/<x>/**` 同提交改 | 不退役 | 同上 + ops-routes + 失效源 |
| 生成物 | `facts.md`、`INDEX.md`、现状块 | 机械事实 | **禁止手改**，`docs write` / `numbers --write` | — | facts / index |
| 验证地图 | `verify-book-corpus/SKILL.md`、`features/*.md` | 用户可见行为 + 逐字验证命令 | 行为变了先改地图（技能自己的规矩） | 功能删掉就删文件 | 失效源 + 已知红失效源 |
| 词表 | `GLOSSARY.md` | 现行名词，一词一义 | 随验证地图改 | 旧词进「已退役术语」节 | 退役词 + 失效源 |
| 决定 | `docs/adr/*` | 为什么 | accepted 后正文冻结 | `superseded` + `替代：` | status |
| 方案 | `docs/design/*`、`docs/briefs/*` | 打算怎么做 | draft/proposed 可改；之后只改状态行 | `implemented`+`验收：` / `superseded`+`替代：` / `historical` | status + since |
| 子系统参考 | `docs/检索/README.md`、`指标口径.md` | 检索层现行口径 | 随检索代码改 | 被替代时标 superseded | status(`living`) + 失效源 |
| 追加账 | `docs/检索/踩坑记录.md` | 踩过的坑 | 只追加；修好的坑在条目末尾加「已修：`<commit>`」 | 不退役 | status(`living`) + 失效源 |
| 记录 | `reports/**`、复盘、带日期的读数快照、`artifacts/verify/**` | 某一天发生了什么 | 一次写成，冻结 | 生来就是 `historical` | status |

## 5. 结构化门禁（把规则改成检查）

| 门禁 | 内容 | 拦得住哪条 |
|---|---|---|
| **G1 状态契约扩面** | `docs/**`（除 `reference/`、`agents/`、`INDEX.md`）与 `reports/**` 首屏都要有状态行。新增状态值 `living`，用于活的参考文档，必须同时写 `失效源：`。只认状态行，删掉 `_is_historical` 里的「布局说明」判断 | D4、D5 |
| **G2 退役词表** | `docs/reference/retired.toml` 每条记：词或路由、退役日期、替代链接。`check_docs_sync` 扫活文档，命中就报错，除非这一行同时含退役豁免词。把文档标成 superseded 时，同一个提交往表里加词 | D1、D6 |
| **G3 失效源全覆盖** | `check_since` 改成扫所有带 `失效源：` 的 md，包括活文档、应用手册、`features/*.md`、`SKILL.md`。映射写进各文档以后，删掉 `sync-docs` Step 4 的手写表 | D2、D6 |
| **G4 提交级耦合** | `pre-commit` 钩子 `docs-coupling`（`tools/check_docs_coupling.py`）：暂存区里的代码命中某份文档的 `失效源：`，而那份文档没一起暂存，就打印警告和文档路径。先只警告，观察一段时间再决定是否改 `--strict` 阻断 | D2、D3 |
| **G5 已知红带失效源** | `features/README.md`「已知红」改成表，加一列 `失效源`。对应文件一改，`--since` 与 `docs-coupling` 就点名这条已知红让人复核 | D3 |

每道门禁上线前均已用历史反例验证：G2 拿治理前 `GLOSSARY.md` 拦下 12 处命中；G3/G5 拿 `92b013c..28d18cb` 点名全部受影响已知红与功能文档；G4 拿 `apps/reading/server.py` 点名 `features/layered-reads.md` 等 4 份文档。

## 6. Agent 改动纪律（写入 AGENTS.md「流程」）

1. 改代码前先跑 `book-corpus docs check --since HEAD`，看哪些文档的失效源会被这次改动命中。
2. 文档和代码在**同一个提交**里改。G4 会提醒。
3. 改了用户可见行为：先改 `features/<x>.md`，再按验证地图跑一遍，把「证明与跳过」里那一行就地改成本轮 RUN_ID。
4. 方案落地的那个提交，把方案状态改成 `implemented` 并写 `验收：`；方案被推翻时改成 `superseded` 并写 `替代：`，同时往 `docs/reference/retired.toml` 加词。
5. 历史文档正文不改，只改状态行。
6. 迭代收尾跑 `sync-docs`，写 `docs/.last-doc-sync`。
