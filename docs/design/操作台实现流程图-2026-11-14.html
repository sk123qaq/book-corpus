流程 01 · 一次点击

一次点击怎么变成一个可回放的任务

输入页面按钮、筛选条件或拖进来的文件→输出job_id + 状态 + 产物（books/、md/、人账、索引）

01

页面动作

apps/ops/web/app.js:233

api() / post() 包一层 fetch；每个页签自己拼 payload。写按钮带 data-write，写任务在跑或排队时前端禁用；拖文件走 wireDrop 直接上传。

决策

页面不保存业务状态：刷新、换标签页、重开浏览器都必须回到服务端的真值。按钮禁用只是提示，服务端还会再拦一次。

读数

8 个导航页签 + PDF 清单子页，共 9 个视图；验收里有一组检查专门对齐「页面状态词」与「驱动状态表」。

02

本机闸

判定apps/ops/server.py:2511

Host 必须是 127.0.0.1 或 localhost（可带端口）；Origin 为空或 http:// 同源。GET 与 POST 都校验，不通过直接 403。

决策

不做登录，只绑回环 + Host/Origin 双校验。GET 也要查：DNS rebinding 的页面同样能读 /api/jobs 和日志下载，只护 POST 等于没护。

本机请求
03

请求分流

server.py:2537 do_GET / :2766 do_POST

GET 只读状态、任务、日志尾部、白名单文件；POST 走 JSON 命令。body_json 上限 1 MB，上传单独走裸 body，上限 2 GB，流式写 .part 再 os.replace。

决策

上传不塞 JSON（base64 会多 1/3 且占内存）；普通命令保持小包。4xx 一律断开连接，避免 keep-alive 下残余 body 被当成下一条请求。

读数

2 GB 上传上限；1 MB JSON 上限；413 测试用 250 字节头续收，确认连接已断。

04

写任务排队闸

判定server.py:2766 + :2825

14 条写路由在 submit_lock 里先查 writer_busy()：有写任务在跑，或队列里有写任务，返回 409；空闲才提交。只读路由不查，直接在 03 转到各自 handler，不生成任务。

busy 检查与 submit 必须原子：两个并发写请求都过了检查，就会各起一个写者抢同一份人账。409 是正常状态，不是异常。

05

调度与执行

server.py:1052 _loop / :1098 _run / :1135 _play

只读任务取 .reader.lock 共享锁，最多 2 个并行；写任务取 .writer.lock 独占。拿锁后回读任务状态，已取消就不启动。每步 spawn 一个进程组，收 rc、日志与 capture 产物。

决策

一写两读。扫描、分诊、查看问题、删书预览都慢，但只写自己的 jobs/<id>/，可以让它们并行；写任务碰批次账与库，必须独占。

读数

READ_SLOTS=2；4 个只读 kind、7 个写 kind；ingest.py 另有自己的 .ingest.lock。

rc + marker
06

语义门槛

判定server.py:537 gate_rc / :840 KINDS

退出码 0 不等于成功：每种任务有自己的 gate。扫描要写出数组 plan.json；入库要 "conflicts": 0 且日志含「未匹配 0 条」；拆章要 report.json 的 pending_review；维护每步要各自的 marker。

决策

门槛放服务端，不放脚本里。脚本仍然可以手跑；页面只在语义结果成立时才说成功。退出码 0 但 marker 没出现，判失败，后续步骤不再跑。

读数

本机 5 条失败记录都带门槛/步骤摘要；其中两条是旧版 verify marker ^全过\s*$ 对不上 全过：N 项，一条是 audit rc=1。没有一次是服务崩溃。

succeeded / awaiting / failed
07

终态与回看

server.py:1205 / app.js:2338

任务落到 7 个状态之一：succeeded、failed、awaiting_review、cancelled、orphaned 等。页面每 2 秒轮询详情，显示步骤、命令行、日志尾部 200 行；可下载、重跑、停止。

决策

轮询 SQLite，不用 WebSocket：stdlib 单进程、刷新不丢、多个标签页看到同一份真值。日志按字节分页，UTF-8 被切断的半个字符退回下一页，不产生 U+FFFD。

读数

日志尾 200 行；单页最多 400 KB；详情页刷新时就地改 DOM，不重置滚动位置。

03

启动与接管

server.py:1008 adopt

服务启动先 adopt() 再 start()。PID 活着且 /proc/<pid>/cmdline 的脚本 basename 与 argv 对得上，才接管并继续看；否则 running 步记 unknown、任务标 orphaned，不杀进程。

决策

先接管再调度：接管来的任务不持 flock，先跑调度会出第二个写者。PID 可能被复用，所以不能只看 PID；argv 对上才认。

读数

168 项验收含「接管续跑」与「孤儿不杀」两组；失联任务不会被当成成功。

运行中
04

取消

判定server.py:1349 _terminate

只接受未结束且非 awaiting_review 的任务。对进程组发 SIGTERM，每 0.25 秒查一次，等 10 秒；组里仍有活口就 SIGKILL。已结束返回 409。

决策

杀进程组，不杀组长：拆章/PDF 会派生 worker，组长退出不代表组里没活口。取消在 _finalize 里优先于门槛，已取消的任务不会被改回成功。

读数

KILL_WAIT=10 秒；取消请求只在 queued/running 时有效。

正常退出 / 被取消
05

收尾与链式任务

server.py:1205 _finalize

门槛通过后写终态。入库成功且本次有 add/replace 的 doc 格式，自动接一个 docs.run；维护成功后台跑 ops_status.py --deep 刷新体检缓存。

决策

文档转 md 单独起任务，不并进入库：一本书转失败不该回滚入库。用 docs-seed.json 记已投递的 uid，重跑不重复转。

读数

仅 lib_common.DOC_FORMATS 且 action 为 add/replace；深体检超时 180 秒，失败只写日志，不反向判维护失败。

日志、重跑与清理

server.py:2677 / :2371

日志不进 DB，放 jobs/<id>/log.txt；/api/jobs/<id>/log?offset= 按字节分页并脱敏。重跑复制原 commands.json，按当前 root 重算解释器。清理保留 90 天 / 200 个任务 / 缩略图 30 天。

日志留文件，DB 只留索引与摘要：几 MB 的构建输出不该撑大 ops.db。重跑不原地复用 job id，旧记录保留可对照。

读数

流程 03 · 读数

顶栏的数字从哪来，什么时候不可信

输入ops_status.py --json + ops.db + PDF 清单→输出三态 + 顶栏 + 总览待办

01

状态请求

server.py:1396 status

GET /api/status 默认走 6 秒缓存；refresh=1 强制刷新，deep=1 连深体检一起跑，最长 120 秒。慢刷新用 status_gen 防止覆盖后发起的新结果。

决策

页面每几秒轮询一次，不能每次都扫 300 万段索引；缓存 6 秒。深体检只在操作员点「刷新状态」时跑，不放在后台定时器里。

读数

STATUS_TTL=6.0；脚本超时 120 秒；刷新在锁外跑，不堵其他状态请求。

--json --root
02

状态脚本

src/bookcorpus/scripts/ops_status.py:509

独立脚本读 library.db、index.db、ledger.db、书目总表、视图与 PDF 账；SQLite 全部只读打开。stdout 取最后一个 JSON；脚本失败或输出不是对象时，服务端填零并记 error。

决策

状态计算放脚本，不塞进 server.py：同一份读数既能给页面，也能在终端跑；服务端只做缓存、三态与加料。

读数

643 行脚本；--deep 是唯一写盘动作，只写 工作区/运维/last-audit.json。

03

完整性检查

server.py:1416 _load_status

complete = source in ("script","fixture")；缺 library/catalog/index/views 任一段进 missing；audit.at 为空或 problems 非空都影响结论。

决策

缺库时计数填 0，但带 ok:false；0 不能当真实读数。页面把这类字段显示成「—」，不显示 0。

读数

problems + missing + audit
04

三态闸

判定server.py:1416

unknown：脚本没跑成或 payload 不完整；degraded：读到了，但缺库、有 problems、或体检没跑；ok：读数完整且无问题。三态之外保留原 ok/error 字段给老消费者。

决策

三态不是二值：unknown 绝不能被读成「健康」。体检没跑也算 degraded——没有体检记录，就不能担保库是干净的。

读数

当次读数：1,956 本、1,823 可读、108,505 章、133 待转、索引 3,006,736 段 / 1,819 本、人账 1,956 行、书目未匹配 0；audit.at=null，所以状态是 degraded。

顶栏字段
06

顶栏渲染

app.js:370 renderStats

藏书、可读、待转、存档、索引、收件箱；索引落后显示「落后 N 本」，索引多出来显示「多 N 本」；读数未知显示「—/未知」。写任务在跑时额外挂一个「写任务在跑」。

未知与 0 必须长得不一样。索引「落后」和「多出来」是两种问题：前者新章搜不到，后者可能含已移出的书，处理方式不同。

总览
07

总览待办

app.js:456 todoItems

按优先级生成待办：状态未知 → 缺库 → 没体检/体检过期 → fail/broken → 书目未匹配 → 收件箱 → 待确认任务 → 电子书 → 待转 → 索引落后/多出 → 体检提醒。首屏主按钮跟着第一条待办走。

决策

总览不是把所有数字铺开，而是给「下一件事」。所以待办有顺序，主按钮只出现一个；状态不完整时先说去维护，不拿局部数字下结论。

08

深体检

ops_status.py:225 / :369

普通模式用计数估索引落后；--deep 用集合差精确算，并跑 audit_state.py --deep。体检缓存只在 root 对得上、deep is True 时采信；library/index/catalog 比体检新就标 stale。

流程 04 · 写入链

新书导入：从收件箱到可检索

输入拖入或上传的文件→输出books/<uid>/source/ + 人账 + library.db + 书目总表 + 可选 md/

01

上传

server.py:2832 api_upload

裸 body 流式收，单文件上限 2 GB；X-Filename URL 解码、去路径、拒绝点文件与 ..；后缀必须在 lib_common.ACCEPT_EXTS。每线程独立 .part，收满后 os.replace。

决策

收件箱里绝不出现半文件：.part 不进清单，只有长度对上才原子改名。同名不覆盖，自动 -2，避免把上一次还没入库的源顶掉。

2 GB 上限；上传中断会删掉 .part 并返回「收到 X / Y」；413 由验收覆盖。

02

扫描

server.py:2884 / gate :552

只读任务跑 ingest.py scan --json --out plan.json --cache classify.json。分类缓存落在本次 job 自己的目录，不写共享的 工作区/批次/ingest/classify.json。

扫描标只读，所以不能碰共享缓存；每个 job 一份缓存，代价是重复分类，换的是扫描可与写任务并行、不会互踩。

plan.json
03

计划编辑

server.py:2904 api_import_plan

逐行改书名、一级/二级、保留、动作、换源 uid。分类可写「一级/二级」字符串，空则落「其他」；replace 必须填 uid；书名不能空；合并后原子写回计划。

决策

人只改差异，不重写整张 CSV。计划就是这次入库的 write-ahead log；页面重新打开时优先带出最近一份仍可用的计划。

读数

04

入库前闸

判定server.py:3005 api_import_apply

计划必须在 工作区/运维/jobs/ 下；不能有 review 行；换源必须有 uid；所有源文件必须还在收件箱，且文件名与计划完全一致。缺分类不拦，归一成「其他」并写回计划。

决策

扫描后收件箱变了就拒绝，而不是「尽量挑还能用的」：apply 必须看到 scan 看到的那份文件集，否则 uid、sha256、替换目标都会错位。

读数

三类 400：还有 N 行待核、N 行换源没填书号、收件箱里没有这个文件；计划路径越界也拒绝。

apply
05

入库执行

ingest.py apply --apply

源文件移入 books/<uid>/source/；人账按 add/replace/delete 更新；结果写 applied.json 给后续文档任务认新书。gate 要求日志里 "conflicts": 0 且含「未匹配 0 条」。

决策

新书不手填人账：ingest.py 是唯一追加者，账表页只能改已有行。这样 uid 生成、目录名、源文件、人账四件事始终同源。

读数

重建派生

server.py:874 rebuild_commands

删书：七层预览，哈希锁住落地

输入uid + 移出理由→输出冷宫里的原书 + 人账/书目库/索引/视图清理 + retired.tsv

01

找人

server.py:2138 retire_search / :2148 retire_drop

按 uid 或书名搜；「不留的书」列表从人账 保留=drop 来。只有书目录真的存在、uid 与目录名一致，才允许往下走。

决策

删书不是「从账里删一行」：账表页的移出只删账，书还在。删书页必须找到真实书目录，否则没有可移出的源。

读数

预览的 blockers 会挡住：书目录不在 books/、uid 与目录名不一致、冷宫 README 表头不是 7 列。

uid + reason
02

七层预览

retire_book.py:387 build_preview

--dry-run --json 只读算出七层：书目录与要删、源文件与共享动作、人账与 DB、expand、奖项、主题/奖项视图、书目表与系列文档；另附冷宫目标、快照、blockers/warnings 与 plan_hash。

决策

预览和落地用同一份 build_preview：落地时重算，哈希不一致就拒绝。哈希只收决定破坏范围的字段，索引行数/时间这些派生读数不进哈希。

读数

源动作按共享本数选：独占源 move，共享源 hardlink；跨文件系统才退回复制。

preview + hash
03

预览闸

判定server.py:3601 api_delete_dry

uid 形如 B1234、理由不能空；job 成功必须落 dry-run.json 且含 plan_hash。页面展示七层清单、冷宫路径、快照是否就绪。

决策

没有哈希就不给落地按钮。预览不是「看一眼」，而是这次删除的契约；库变了，旧预览作废。

读数

快照目录 books.snapshot-YYYY-MM-DD 缺失会挡住 apply（--no-snapshot 只给测试）。

uid + hash + 勾选
04

落地闸

判定server.py:3626 api_delete_apply

服务端要求：uid 格式、confirm_uid 与 uid 完全一致、plan_hash、理由、confirm is True、当前无写任务。命令带 --plan-hash；脚本重算预览，不一致直接拒绝。

决策

两道人工确认 + 服务端勾选校验 + 脚本哈希校验：前端 checkbox 不能是唯一防线，脚本入口也不能绕过人确认。

读数

168 项验收含「删书预览与应用」；哈希不一致、uid 不一致、没勾选都会被拒。

--apply
05

移出与清理

retire_book.py:688 apply

独占源移动、共享源硬链接到 books/_冷宫/<书名>/source/；删 md/html/json；删索引里的 expand、para、book_concept 行并重建 FTS；删 expand md；写 retired.tsv 与冷宫 README。

决策

冷宫只留 source：阅读派生都能重建，原书不能。共享源不复制整本，用硬链接，删书不额外吃掉几十 GB。

读数

失败会写带 note 的 retired 行，但不会被当成成功记录；重跑能补。冷宫目录同名时带 uid。

重建
06

重建派生

retire_book.py:640 rebuild_derived

直接删索引行后依次跑 build_library.py --emit-json、gen_book_catalog.py、build_views.py；如果删了 html，再跑 build_index.py。任一步 rc 非 0 抛错，不留「删了一半还说成功」。

决策

索引行直接删 + FTS rebuild，不等整库重建：删一本书不该扫 300 万段。书目库/总表/视图仍走标准脚本，保证和日常路径同源。

读数

重建成功后才写成功行；失败补失败行，重跑靠 pending 快照续。
