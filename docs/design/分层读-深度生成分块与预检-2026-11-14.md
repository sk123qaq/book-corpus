# 分层读深度生成：分块、输出预算与预检

状态：implemented · 2026-11-14
验收：uv run --frozen pytest -q；uv run --frozen book-corpus docs check --data-root /home/shike/书库；uv run --frozen book-corpus verify --root /home/shike/书库

范围：`skim / standard / deep` 三档中，`deep` 的结构模型（`model` 层）与后续层的生成调度、分块、输出预算、失败分类、提交前预检。

不包含：三档与读法模式本身（见 [`分层读-方案-2026-11-11.md`](分层读-方案-2026-11-11.md)）；视觉读本；正文质量与模型内容正确性；已有深度包的批量回填。

## 一句话

深读生成不再假设一章能塞进一次模型调用。按块数分块，按块给输出预算，提交前预检，超限的源文件先拆章。目标不是让 B0019-08 通过，而是让任何一章要么在预算内跑完，要么在花模型调用前被明确拒绝。

## 问题

### B0019-08 的失败

2026-11-14 10:32:54，B0019 第 8 章「第三章世间已无张居正」提交深读，10:54:23 失败，耗时 21 分 29 秒。失败账在 `工作区/阅读/failures/r-0b75993eeb-model.json`，错误原文：

```
连续 2 次未通过校验：uid 不一致：B0019-C04 != B0019
```

任务账与事件日志显示的过程：

1. 第一次生成用默认 `chunk_chars=18000`，计划 3 块。C01 是 3 字的标题块；C02 是 B02 到 B88，87 块、17,989 字，输出到 32,768 token 时 `finish_reason=length`，耗时 300.3 秒；C03 未执行。
2. `service.py` 捕获 `ModelTruncatedError`，整章改用 `chunk_chars=9000` 重跑，计划 4 块。C01、C02、C03 通过并落缓存，C02 中途还重试过一次。
3. C04 是 B88 到 B158，71 块、6,432 字。10:52:17 第一次输出 16,866 个 completion token，校验失败；10:54:23 第二次输出 12,980 个，仍失败，任务终止。
4. 8 次模型调用中，1 次截断，C04 两次被拒。总耗时 21 分 29 秒。

根因有两条，必须一起修。

第一条是信封字段校验过严。`depth/model.py:375` 的 `_chunk_payload` 用 `data.setdefault("uid", chapter_view.get("uid"))`，模型自己给了 `uid` 就原样保留。`depth/schema.py:393-395` 要求 `model_uid` 与章节 `uid` 严格相等，不等就 `_fail`。B0019 的章节块 id 是 B01 到 B158，真实数据里没有 `B0019-C04` 这个字符串。模型把书号 B0019 和分块前缀 C04- 拼成了顶层 `uid`，校验器不接受，合并阶段却会用 `chapter_view` 覆盖 `uid`，两处语义不一致。原始输出没有留存，`raw_payload` 是 `null`，所以「模型为什么这样写」只能推断，不能证明。

第二条是容量没有上限。18,000 字的 C02 有 87 块，模型输出到 32,768 token 被截断。整章回退到 9,000 字后，C04 仍然要一次生成 71 块。当前代码没有块数上限，也没有提交前预检，只有失败后的整章重跑。重跑会把已完成的分块缓存保留下来，但也会把一次容量失败放大成 21 分钟的任务失败。

## 目标与非目标

目标：

1. 任何深读任务最终只有三种状态：`done`、`blocked`、`failed`。`blocked` 表示源文件超限，没有调用模型，消息里给出块数、分块数、预计 token、预计耗时和拆章建议。`failed` 必须带具体 `error_kind` 和原始 payload，不再出现 `unexpected`。
2. 通过预检的章，正常运行时不再因为 `finish_reason=length` 失败。截断只允许发生在单个分块上，并且只重试这个分块。
3. 一个大的 `md/` 文件可以拆成多个 md 文件。拆分后每个文件重新提交，预检通过，任务正常跑，不需要改代码。
4. 续跑复用已完成的分块缓存。一个分块失败不会让其他分块重新调用。
5. 操作员在提交前能看到块数、分块数、最大块块数、预计输出 token、预计耗时和预检结论。

非目标：

- 不把全局 `MAX_TOKENS` 提到 150,000。
- 不在任务内部自动拆分 md 文件。拆分由操作员做，应用负责告诉他要拆到什么程度。
- 不改三档、读法模式、面板和正文。
- 不批量回填或删除已有深度包。
- 不把模型内容质量问题当成容量问题。容量预检只判断「这次调用能不能在预算内完成」，不判断「模型写得好不好」。

## 阈值与判定

### 定义

- `blocks`：`Library.read_chapter` 返回的正文块数，包含空文本块。空文本块仍占一个块位和一个分块名额，模型仍会为它输出，所以不把它从容量判断里去掉。`chars` 只统计非空文本。
- `chunks`：用 `_chunk_plans(blocks, chunk_chars=18000, max_blocks=100)` 算出的分块数。预检和生成共用同一个规划函数。
- `max_chunk_blocks`：规划结果中单块的最大块数。
- `estimated_output_tokens`：`ceil((chunks * 2000 + blocks * 800) * 1.2)`。2,000 是每块的表头、引用和 JSON 开销，800 是每块的正文输出估计，1.2 是安全系数。
- `estimated_seconds`：`ceil(estimated_output_tokens / 109)`。109 token/s 是 B0019-08 在 32k 输出上的实测速度，后续用日志校准。

这些是起始值，不是永恒常数。实施后前 20 个真实任务要用日志重算 `TOKENS_PER_BLOCK`、`TOKENS_PER_SECOND` 和安全系数。

### 提交前判定

| 条件 | 结论 | 提示 |
|---|---|---|
| `blocks > 5,000` | 直接不做，`source_too_large` | 单章超过 5,000 块，约 400 万字符；给出实际块数与拆章建议 |
| `chunks > 100` | 直接不做，`source_too_large` | 超过 100 次模型调用，单次失败概率叠加后不可接受 |
| `estimated_output_tokens > 1,000,000` | 直接不做，`source_too_large` | 超过约 2 小时的输出预算 |
| `estimated_seconds > 7,200` | 直接不做，`source_too_large` | 按 109 token/s 超过 2 小时 |
| `blocks > 1,000` 或 `chunks > 20` 或 `estimated_seconds > 3,600` | 允许提交，警告 | 显示「会切成 N 块，预计 X 分钟」，让操作员知道这不是一次调用 |
| `max_chunk_blocks > 100` | 允许提交，提示会切块 | 阶段 2 会按 100 块上限切开，不因为当前规划块大就拒绝 |
| 其他 | 通过 | 正常提交 |

`blocked` 的响应形状：

```json
{
  "error": "本章 48,029 块，超过单章上限 5,000 块；按 100 块切分约 481 个分块、约 47,262,240 输出 token、约 120.4 小时。",
  "code": "source_too_large",
  "stats": {
    "blocks": 48029,
    "chars": 2413512,
    "chunks": 481,
    "max_chunk_blocks": 100,
    "estimated_output_tokens": 47262240,
    "estimated_seconds": 433599,
    "limits": {
      "blocks": 5000,
      "chunks": 100,
      "tokens": 1000000,
      "seconds": 7200,
      "max_blocks_per_chunk": 100,
      "max_tokens_per_chunk": 96000
    }
  },
  "remediation": "把 md/ 中的这个文件按章节或每 100 块拆成多个 md，再对每个 md 提交深读。"
}
```

HTTP 状态用 422。提交时拒绝不创建任务，不写失败账，不调用模型。任务已经在队列里、提交后源文件又变大时，运行开始处再判一次，状态记为 `blocked`，不是 `failed`。

### 拆章目标

预检是硬门槛，拆章目标是操作建议。按 800 token/块、109 token/s、1.2 安全系数和 2 小时预算，一个 md 大约 780 块是上限。推荐拆到每份 500 块左右，约 1.3 小时，留出模型变慢的余量。48,029 块的 B0041 著者序大约要拆成 96 份；按书本身的章节边界拆更好，不必机械按 500 块切。

拆分后每个 md 都是新的章，`source_sha256` 变化，旧缓存自然失效。重新提交时预检读取新文件，块数下降，任务正常跑。应用不自动改 `md/`，只给建议和实际数字。

### 输出上限

| 调用 | 输出上限 | 截止 | 说明 |
|---|---:|---:|---|
| 注解与其他普通调用 | 32,768 | 1,200 秒 | 保持全局 `MAX_TOKENS` 不变 |
| 深读分块调用 | 96,000 | 1,200 秒 | 100 块 × 800 token + 开销约 82k，96k 有约 17% 余量（未乘 1.2 安全系数） |
| 深读分块的硬上限 | 128,000 | 1,500 秒 | 只在 100 块仍截断时对该块使用，不作为默认 |
| 150,000 | 不作为默认 | 1,800 秒 | 只作为实验；150k 按 109 token/s 约 1,376 秒，已经超过 1,200 秒 |

96k 是单次深读分块的上限，不是全局默认。`ModelClient.max_tokens` 仍可由 `READING_MODEL_MAX_TOKENS` 覆盖，但深读调度会给每个分块传自己的上限，缓存键也带这个上限。

## 实施方案

### 阶段 0：预检与规模报告

先做这一阶段。它不改生成质量，只把「这个源文件该不该提交」变成提交前的确定判断。

0.1 新增 `src/bookcorpus/reading/depth/preflight.py`。

- `Limits` 数据类，字段为 `max_blocks_per_chunk=100`、`max_tokens_per_chunk=96000`、`max_blocks_per_chapter=5000`、`max_chunks_per_chapter=100`、`max_output_tokens_per_chapter=1_000_000`、`max_seconds_per_chapter=7200`、`tokens_per_block=800`、`tokens_per_chunk_overhead=2000`、`safety=1.2`、`tokens_per_second=109`。
- `evaluate(blocks, plans, limits)` 返回 `Gate`，字段为 `ok`、`code`、`warnings`、`stats`、`remediation`。
- `SourceTooLarge` 继承 `RuntimeError`，带 `kind="source_too_large"`、`stats`、`to_dict()`。
- 纯函数，不读模型、不写缓存、不碰盘。输入是 blocks 和已算好的 plans，输出是判断。

0.2 给 `_chunk_plans` 加 `max_blocks` 参数。

- 现有 `chunk_chars` 保留，默认 18,000。
- `max_blocks=None` 时行为不变，旧调用和旧测试不受影响。
- 传入 `max_blocks` 时，`_split_at_limit` 同时受字符上限和块数上限约束。
- 新增公开包装 `plan_chunks(blocks, chunk_chars=18000, max_blocks=100)`，预检和生成都调它，避免两份规划逻辑漂移。

0.3 在 `ReadingService.submit_depth` 入队前预检。

- 位置是 `src/bookcorpus/reading/service.py:1049` 附近。读完 `raw = self.library.read_chapter(uid, n)` 之后、`queue.submit` 之前。
- 用 `plan_chunks` 算 plans，再 `evaluate`。不通过就抛 `SourceTooLarge`。
- 预检不看 `requested` 是否包含 `model`；任何深读任务遇到超限源文件都在提交前拒绝。
- 通过后把 `stats` 和 `warnings` 记进任务账，UI 能显示「预计 N 块、X 分钟」。

0.4 在 `_run_depth_job` 开头再判一次。

- 位置是 `src/bookcorpus/reading/service.py:1339` 附近，读完 blocks 之后。
- 防止提交后 md 被替换或追加。第二次不通过时抛同一个 `SourceTooLarge`。
- `src/bookcorpus/reading/jobs.py:347` 的 `_run_one` 把 `error_kind == "source_too_large"` 映射为 `state="blocked"`，保留 `stats` 和 `remediation`，不提供「重试」按钮。

0.5 `apps/reading/server.py` 的 `_post_depth` 捕获 `SourceTooLarge`，返回 422 和上面的 JSON。

- 现有错误分支保留 400 `MissingConfigError`、404 找不到章节、409 `job_active`。
- 422 只用于源文件超限，不复用 400，避免客户端把「配置缺失」和「文件太大」混在一起。

0.6 阅读页的深读工单表单显示预检结果。

- 表单在 `apps/reading/web/chapter.html` 与 `apps/reading/web/assets/app.js`。
- 提交前显示块数、预计分块数、预计耗时。超限时按钮置灰，显示 `remediation`，并给出 `books/<uid>/md/` 路径。
- 不显示「重试」；显示「去拆章」和「查看 md 目录」。

0.7 新增规模报告脚本 `tools/chapter_size_report.py`。

- 只读扫描 `BOOKS_ROOT`，输出 JSONL 和 CSV，含每章 uid、n、字符数、块数、18k 计划块数、最大块块数、9k 计划块数。

## 原因

### 为什么按块数，不按字符数

字符数和输出 token 不是一条直线。B0019-08 的 18,000 字 C02 有 87 块，输出 32,768 token 被截断；9,000 字 C02 只有 40 块，输出 31,304 token，仍然接近上限。块越多，JSON 的块条目、引用、局部 id 和结构字段越多，输出增长比字符数快。按字符切块会把「87 块、18,000 字」和「87 块、60,000 字」当成两种不同的风险，实际风险一样。按块切块直接约束输出量。

### 为什么是 100 块

100 块不是质量阈值，是延迟和缓存粒度的折中。84.5% 的章总块数不超过 100，一次调用能完成；总块数 p90 是 131，切两块；18,000 字计划的最大块 p99 是 348，切四块。100 块乘 800 token 加 2,000 开销约 82,000 token，96k 有约 17% 余量；这是未乘 1.2 安全系数的期望值，预算估算乘 1.2 后是 98.4k，所以 100 块仍可能截断，阶段 2 用二分兜底。再大，单次调用接近 1,200 秒截止；再小，普通章会被切得太碎，调用数和失败面都上升。

### 为什么是 96k，不是 150k

150k 按 109 token/s 约 1,376 秒，已经超过当前 1,200 秒的流式截止。把截止提到 1,800 秒可以让 150k 跑完，但单次调用可能 23 分钟，操作员等不起，失败重试的成本也更高。更关键的是 150k 仍然覆盖不了尾部。p99.9 的最大块是 710 块，3,040 块按 782 token/块约需 238 万 token，150k 连零头都不够。把 150k 当默认，只是把失败点从 87 块推到 400 块左右，长尾照样失败。96k 加 100 块上限，是把「一次调用」限制在一个可预测的范围内，超出就切块或预检拒绝。

### 为什么预检拒绝，而不是让任务失败

48,029 块的 B0041 著者序已经不是一章，是一个没有拆开的书。任何输出上限都不能让它在一次调用里变成一个合法 JSON。提交后花 21 分钟再失败，比提交前 50 毫秒拒绝贵得多，而且失败账里只有一句「uid 不一致」，操作员看不出真正原因是源文件太大。预检拒绝把原因、数字和下一步写清楚，状态是 `blocked`，不是 `failed`。这不是逃避失败，是把不可执行的输入挡在模型调用之前。

### 为什么全局仍是 32,768

注解、速览和其他普通调用不需要 96k。把全局提到 96k 会让所有调用的最坏延迟变长，缓存键变化，成本上升，而且没有证据表明这些调用需要更大的输出。深读分块需要 96k，是因为它一次要生成几十个块的完整结构。上限应该跟着调用类型走，不跟着全局常量走。

### 为什么保留原始 payload

这次失败的 `raw_payload` 是 `null`。我们只能从缓存里的 C01、C02、C03 推断模型会把 `uid` 写成 `B0019-C04`，不能证明 C04 到底怎么写的，也不能排除它还有别的结构错误。下一次失败必须留下原始输出，失败账才有复核价值。200 KB 的上限足够放一章的 JSON，超过时写 `payload_omitted`，不静默丢。

### 为什么稳定块 id

当前 `plan_signature` 包含 `index`、`total`、`id_prefix`。切开一个块，其他块的 `index` 和 `total` 都变，签名全变，缓存全部失效。B0019-08 的 21 分钟里，C01、C02、C03 已经成功，C04 失败；如果重跑时整章重新规划，前面三块白跑。稳定块 id 让缓存按块范围命中，切一块只影响这一块。

## 风险与回滚

风险：

- 100 块上限会让 23% 的章从一次调用变成多次调用。预检的 2 小时上限防止无限拆分。
- 96k 单次调用比 32k 慢。1,200 秒截止是硬边界，模型变慢时可能先触发截止而不是截断。重试会切块，不会无限等。
- 改 `max_blocks`、`max_tokens`、`chunk_chars` 会让深度分块缓存失效。注解缓存不受影响。B0019-08 的一次性重跑可以接受。
- 预检阈值可能误伤边缘章。500 块的章约 400k token、4,400 秒，能通过；900 块的章约 864k token、7,900 秒，会被拒绝。操作员可以拆章，也可以临时调高预算。
- 模型或 provider 变化会让 109 token/s 和 800 token/块失准。前 20 个任务必须用日志校准。

回滚：

- `READING_DEPTH_PREFLIGHT=off` 关闭提交前预检，任务回到旧行为。
- `READING_DEPTH_MAX_BLOCKS=0` 关闭块数上限，回到只按字符切块。
- `READING_DEPTH_CHUNK_TOKENS=32768` 把深读分块上限降回全局值。
- `READING_DEPTH_PLAN_HINT=off` 关闭计划提示，重跑每次都从头规划。
- 回滚只改环境变量，不改数据。旧缓存是否命中取决于 `cache_key` 的输入是否也回滚到旧值；不命中时按 miss 处理，不会拼错块。
