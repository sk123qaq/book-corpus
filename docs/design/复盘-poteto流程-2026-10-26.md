> **布局说明（2026-11-02）**：本文写于 v1 布局。旧示例里的 `库/…` 现在对应 `books/<uid>/…`，`目录/library.db` 对应 `build/library.db`，`目录/检索/` 对应 `build/检索/`，`视图/` 对应 `build/views/`，`工作区/脚本/` 对应 `src/bookcorpus/scripts/` 或 `book-corpus` 子命令。正文保留当时写法，按此表读。


## 0. 一句话结论

你把 poteto 用成了一套证据制度，这部分做得比大多数人好。你没把它用成一套交付制度。缺的那一半集中在三件事上，版本控制、实现委派、界面验收。项目最后基本做成了，靠的是你的判断力和验收脚本，不是流程本身在推。

如果只改三件事，按这个顺序。

1. 开工第一天就 `git init`，每个验证过的单元提交一次。
2. 实现默认交给 `poteto-agent`，父线程只做设计、审 diff、跑验收。账本和文档编辑留在父线程。
3. 任何界面类改动，先有能点、能截图、能断言的验收，再让人看。

## 2. 你做对的八件事

### 2.1 每个阶段都有数字门槛，门槛可复跑

L0 到 L5 每一层都写了判据，`verify_phase.py` 把六箱做成一条命令，末行「全过」才算过。检索层另有 `check_p1.py` 的「失败 0 项」、`probe_b6.py` 的「ALL PASS」、书目表的「未匹配 0 条」。333 次验收脚本调用说明这不是写在纸上给人看的门槛。

这是 poteto 的 **Prove It Works** 用到了项目尺度。它让 22 GB 的搬迁、1,700 多本书的重构、6.4 GB 的索引都能在改坏后被指出来。

### 2.2 三本账，一个字段一个写入者

人账 `分类表.csv` 只由人改，机账只追加，`book.json` 与 `library.db` 是投影，`ingest.py` 与 `classify_books.py --add-new` 共用一个人账文件且要求同一时刻只跑一个。这是你自己发明的账本纪律，比 poteto 的决策账更硬。

它挡住了这类项目最典型的坏法，同一本书的元数据在三个地方各说一套。现在 `conflicts=0` 是可查的。

### 2.3 决定必须带理由和证据指针

`决策记录.tsv` 六列，每行有「为什么」和「证据在哪」，不写散文。70 行里大量是量出来的数字，比如批量 12 在 4/6/12 都是 94%、40 掉到 77%，73 本图册不转，42 本日文暂缓。

这是 **show-me-your-work** 的正确形态。审你的人不需要读会话，跟着指针就能核。

### 2.4 先普查，再动手

540 本 PDF 先做页数、字体、逐页文本量、图片分辨率普查，再抽页算 ink 与文字行带，再判语种，才分诊到文本层与 OCR。结果是不转 73 本图册、暂缓 42 本日文，这两个决定省下的额度和返工远大于普查成本。

poteto 的 **Attack the Premise** 在这里是你执行的，不是模型执行的。你先问「这 540 本真的都需要转吗」，而不是直接开转。

### 2.5 参数用实验定，不猜

批量大小、并发 4 到 8、扩展预算 60/80/120 秒、书级打分默认 `best_support`、卡数默认 6，每个数背后都有一次对照实验或 heldout。B2 的 20 题 heldout 还带 sha256 冻结。

这是 **Explain the Number** 的实践。多数项目在这一步会写「经测试效果良好」，你写的是具体读数。

### 2.6 一次性脚本都做成了可重跑的工具

64 个脚本、17,731 行，加上 5,473 行验收。`check_ops.py` 自己造临时根、写 stub、不碰真库、不调模型，末行 `ALL PASS`。`shot_ops.py` 连浏览器一起查。

这是 **Build the Lever**。你留下的不是结论，是能重跑的机器。这一点在长项目里最值钱。

### 2.7 上下文满了就写结构化交接

11 次交接，格式稳定，`Goal`、`Done means`（含可复制的命令与判据）、`State`、`Landed`、`Decisions`、`Files`。10-23 那份 brief 里连「本机不是 git 仓库，回滚只能靠快照」都写了。

这让 11 次上下文重置没有变成 11 次重来。**Guard the Context Window** 的替代做法，你做到了及格线以上。

### 2.8 把踩过的坑写成规则，不只写结论

`目录/检索/踩坑记录.md` 按 A 到 G 分类，四列，现象、根因、别再这么干、正确做法，每条带证据位置。10-18 的硬链接原地写事故也变成了 AGENTS.md 的「tmp 加 `os.replace`」规则。

这是 **Encode Lessons in Structure**。坑账比复盘文档有用，因为它是查的，不是读的。

### 2.9 允许被推翻，也主动推翻

「先不要一个一个检查旧 md，用新的生成方法替换也许更快」直接省掉几天。唐诗学书系移入冷宫、伪查询实验重做、`没达到 5 个点会不会是本来基准就高` 引出 heldout，这四次都是你自己发起的前提攻击。

这是整个项目里回报率最高的行为。模型很少主动做这件事，你做了。

## 3. 缺失与不足，按代价排序

### 3.1 Git 迟到了七天，而且不是不知道

项目 10-18 开工，10-25 13:52 才有第一次提交。中间 748 次主线程改文件，绝大多数发生在没有版本控制的时候。10-22 的会话里，模型把 `git init` 写在 Phase 0，标了「10 分钟」，然后因为「不想不问就初始化」停住了。你当时说的是「git 不要私有远端」，不是「不要 git」。

代价有三处具体证据。10-23 的交接 brief 只能写「项目不是 git 仓库，回滚依赖快照或文件级备份」。10-22 你手删了几本书的目录，流程只能事后对账。10-18 的硬链接事故靠 `L4-前` 副本才恢复。

poteto 的 Feature、Bug fix、Hillclimb 三条 playbook 都要求按单元提交。没有 git 时，这些门全部落空。

### 3.2 实现基本是主线程写的

748 次 `edit`/`write` 对 25 次 `poteto-agent`。9 个会话改了 20 个以上文件且一次子代理都没开，包括检索层落地那次 55 次、操作台那次 54 次，两次的子代理都是零。17 个 poteto 会话完全没用子代理。

代价不是钱，是上下文和审阅分离。上下文烧得快，于是有 11 次交接。代码由写它的人自己验收，于是界面 bug 由你发现。Feature 第 4 步要求的「父线程审 diff」在多数会话里退化成了「父线程写、父线程看」。

你控制成本是对的，10-21 就指定了子代理用 `deepseek-v4.1-flash`。但委派的意义是审阅分离和省上下文，不是换便宜模型。机械改动确实可以自己写，20 个文件以上的实现不该自己写。

### 3.3 数据层验证很硬，界面层验证是补的

35 条提交里 10 条是「验收」或「补一条检查」。操作台的几个问题都是你先点出来的，扫描收件箱后计划为空、单个勾选框没反应、全选后重拆勾选被取消、staged 算什么状态、PDF 分诊失败。这些正好是交付前该由自己的 lane 抓到的东西，不用十条云 lane，一条能点的本地驱动就够。

`check_ops.py` 和 `shot_ops.py` 后来写得很好，但它们是跟在你报 bug 后面长出来的。poteto 要求「在真实表面验证」，这里的真实表面是浏览器，不是 HTTP 接口。

### 3.4 决策账在 10-24 断了，两套账都没说清谁是主账

最后一行的 15:50 之后，10-25 和 10-26 的全部工作只剩提交消息，35 条提交也都落在这两天。AGENTS.md 仍然把 `决策记录.tsv` 叫「执行期主账」，这句话现在不成立。

代价是「为什么」丢了。提交消息能说清改了什么，说不清当时排除了哪些方案。10-25 的 UI 重做、10-26 的 front matter 索引修正，都只有结论没有取舍。两份账同时存在时，读者会默认旧的那份还在更新。

### 3.5 playbook 选了，但没有执行到底

`how` 读了 9 次，`feature` 9 次，`bug-fix` 7 次，`architect` 3 次。`interrogate` 一次没读，`swarm` 和 `arena` 一次没读，`benchmark-checklist` 一次没读，而检索层做了一周的评测。throughput checkpoint 只在 36 处出现，多数是只读调查的 `n/a` 那一行。

你用一个更硬的东西补了 `interrogate`，`grill-me` 用了 6 次，在操作台和 PDF 重做前把 25 个决定问了一遍。这是有效的替代。缺的是评测那一块，跑了一周数字却没有先读评测纪律的那份清单。

### 3.6 数字没有随数随解释

21 次理解类提问，`recall@10 是什么`、`MRR 是什么`、`long_share@10 是什么`、`gap 是什么`、`cap 占比是什么`、`60 题 gold 是检验的意思吗`。这些定义后来补进了报告，但是在你问之后。

poteto 要求「每个论断在同一句里带证据或标签」。数字没有定义，等于没有证据。代价是你要花回合去追定义，决策被推迟。

### 3.7 进度要靠你打断才拿得到

29 次带「先停下」「进度」「现在在做什么」的打断，17 次直接问进度。这个模式说明汇报节奏不够密，不是你控制欲强。你在为「不知道它在干什么」付费。

poteto 的检查点本来就该在每个验证单元结束时出现在回复里。实际是长段落做完才汇报，所以你要在段落中间叫停。叫停本身又消耗一个回合和一段上下文。

### 3.8 文档和 DB 的同步靠你提醒

10 次明确的「更新 AGENTS.md」「相关的数据库也更新到最新了吗」「把这几处写进 README」。后来 `audit_state.py --deep` 把漂移检查自动化了，这是正确的收尾，但它是被提醒出来的。

现在还有活的漂移。AGENTS.md 写 1,693 本、1,571 本有 md、122 本待拆，今天 DB 是 1,779、1,649、132。AGENTS.md 说踩坑记录「六类四列」，文件里已经是 A 到 G 七类。第一个被新会话读的文件，数字是错的。

### 3.9 评测题集和默认值同源

60 题 gold 既用来选默认方案 `best_support`，又用来定 0.883 的门槛。20 题 heldout 是 10-23 才补的，补得很对，但默认值仍然是在 60 题上选的。

这不一定是错的，样本小的时候没有更好的办法。风险是门槛读数不是样本外读数，下次改动如果只跑 60 题，等于在训练集上报成绩。

## 4. 为什么会这样

项目的形状和 poteto 的假设错位。这是单机、无远端、长批次、大量一次性脚本的个人项目。poteto 的一半篇幅在 PR、lane、merge、babysit 上，这里没有落点。能落地的部分，验证、账本、交接，你抓得很紧。落不了地的部分，分支、独立评审、界面 lane，没有本地替代品，于是默认由主线程兜底。

第二个原因是你把「问清楚」当成控制手段。不确定就停，停完再问。这个习惯本身没错，25 个决定问一遍比做完再推翻便宜。问题在于它替代了流程里的两个机制，一个是 agent 自己的 interrogate，一个是持续的状态汇报。你成了调度器，agent 成了执行器。

第三个原因是不可逆动作来得太早。删书、移冷宫、清批次区都发生在工具成熟之前。你后来补了 `retire_book.py` 和冷宫规则，方向对，但第一版是靠手做加事后对账。

## 5. 下次的流程

这套流程按你的项目形状改过，保留 poteto 的门，去掉用不上的 PR 段落。

### 5.1 开工 20 分钟，四件事

1. `git init`，写 `.gitignore`，第一次提交只含账本、脚本、方案。不跟正文，你的规则已经写好了。
2. 一页纸写清四行。目标是什么，判据是什么，退出条件是什么，分几批。退出条件必须是可判定的谓词，比如「待转 pdf 为 0」或「60 题里 hit@10 不低于 0.9」。
3. 给每条工作流点名 playbook，写在 todo 第一行。实现用 Feature，修 bug 用 Bug fix，只读调查用 Investigation，调一个指标用 Hillclimb，长批次用 Autonomous run。
4. 列出「只能我做的决定」，其余默认让实验回答。写进 AGENTS.md，省掉每次现问。

### 5.2 每个工作单元，六步

1. 先定数据形状。账本加哪几列，JSON 哪些字段，状态机几个状态。形状定了再写逻辑。
2. 先写验收。一条命令，末行给判据。界面类要先能起服务、能点、能截图。
3. 委派实现。给 `poteto-agent` 三样东西，文件范围、数据形状、成功命令。父线程不写实现，只审 diff。
4. 跑验收，贴原始输出。代理指标不算，比如「编译过了」不算。
5. 提交。一个单元一条，消息里写判据。失败的回滚，不留「也许有用」的改动。
6. 决策账加一行，带证据指针。只有取舍和验证结果值得记，流水账不记。

例外只有两类。账本和文档编辑留父线程，因为写入者规则要求这样。少于 20 行的机械改动可以自己来，但要说明为什么不分派。

### 5.3 报告节奏

每三个单元，或者每 90 分钟，给一行。完成了什么，下一个是什么，卡在哪，需不需要你。

写进 AGENTS.md 的一句话。「每个验证单元结束时在回复里给一行状态，不要等我问。」这一条能消掉那 29 次打断的大部分。

### 5.4 界面类改动

先有 `check_ops.py` 这样的断言，再有页面。断言覆盖交互，不只是 HTTP 200。勾选框联动、全选与单选的互相影响、空计划、任务状态词，都要有对应检查。

判据写成一句话。操作人不能在一分钟内点出问题。做不到就不算完成，不许用「页面能打开」交差。

没有 `control-ui` 就自己写一个最小驱动，`shot_ops.py` 已经是半成品，把它当 lane 用。

### 5.5 评测类工作

先读 `benchmark-checklist`，再出第一个数字。

harness 要打印三样东西，指标定义、样本量、噪声或方差。报数只报三件套，值、定义、基线。

gold 和 heldout 分开。默认值在 gold 上选，发布判据在 heldout 上读。两边都跑不出差异时，说「样本不足以分辨」，不要挑一个当赢家。

### 5.6 长批次

退出条件写成谓词，额度用尽、无待转、连续 N 次失败跳过，三选一或者组合。每批落 worklist、logs、skip 账。断点续跑要有一次真实中断演练，不然「能续跑」只是声明。

额度类失败要分类。403 code 12001 和 429 不是一回事，你的踩坑记录已经写清了，新批次照抄这三类。

### 5.7 收工与交接

交接沿用你现在的格式，加一行「下一步的第一条命令」。这行能省掉接手会话的第一次探索。

收工前跑 `audit_state.py --deep`，把文档与 DB 的漂移清零。漂移没清零就不要写「已完成」。

## 6. 本周就能改的五件事

1. 把 AGENTS.md 里的硬编码数字换成查询命令，或者每次由脚本回填。现在它落后 86 本书，会误导下一个会话。
2. 给 `决策记录.tsv` 一个收口行。写明 10-25 起 git log 是主账，或者把 10-25 之后的提交补成决策行。不要留两套账。
3. 在 AGENTS.md 加三句。单元结束报一行，实现默认委派，界面改动先有交互验收。
4. 把「六类四列」改成「七类四列」，或者让 `audit_state.py` 检查文档里的分类数与文件一致。
5. 下一次评测前，先跑一遍 `benchmark-checklist` 的要求，把指标定义写进 harness 输出。这一条只花半小时，能省掉后面每次「这是什么意思」。

## 7. 一页速查

| 你要做的事 | 用哪个 playbook | 必须留下的产物 | 判据 |
|---|---|---|---|
| 加一个功能 | Feature | 数据形状、验收命令、提交 | 验收末行给判据，父线程审过 diff |
| 修一个 bug | Bug fix | 复现命令、根因、失败转通过的输出 | 同一表面复现消失 |
| 搞清楚现状 | Investigation | 带证据的回答，`n/a` 的 checkpoint | 每个论断同句带证据 |
| 调一个指标 | Hillclimb | 冻结的 harness、decision.tsv、每次一条提交 | 指标过噪声且回归门绿 |
| 长批次、无人值守 | Autonomous run | 谓词、worklist、logs、skip 账 | 谓词为真，或明确报死路 |
