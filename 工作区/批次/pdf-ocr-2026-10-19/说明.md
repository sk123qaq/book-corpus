## 一条流水线的状态都在磁盘上

```
worklist.tsv                    范围账，只写一次
work/<uid>/chunks.json          分片账：range / jobId / attempts / queue_rounds / status
work/<uid>/chunks/c%04d/        pilot 的 --out；有 paddle_run.json 就算这一段完成
work/<uid>/merged/pages+run.json  连续页序的逐页输入（doc_0001.md…），交给拼装器
out/<uid>/                      拼装好的暂存 crate
logs/<uid>.json / <uid>.log     结果记录与工具输出
review/<uid>/p%04d.png          逐页体检挑出的可疑页原图，给人看
tests/                          离线测试（不调接口）
```

崩了直接重跑：完成的分片跳过，已受理未下完的分片用账上的 jobId 续跑。每次运行给每一段新的
阶梯预算（`attempts`/`queue_rounds` 归零），所以重复运行不会把上一轮的退避次数带进来。

## 分片与失败分类

分片按 15 MB 估（`MAX_SLICE_MB`），页数夹在 25 到 150。依据：官方上限是本地文件 50 MB、单请求
1000 页；实测 29.9 MB 的切片第一次上传就 180 秒超时，56.6 MB 与 118 MB 直接断，而 11.8 MB、
14.2 MB 能拿到干净回话。

注意 15 MB 是软目标：`MIN_CHUNK_PAGES=25` 是下限，页密度大的书实际切片会超过 15 MB。
2026-10-19 整批首波实测到 24.2–28.2 MB（B1291/B0580/B0579，均 ≤300 页组），仍远低于 50 MB
上限，上传与解析正常；全 worklist 里页密度 >0.6 MB/页的只有 5 本（另两本 B1545/B1556 在 >300 页组）。

失败按接口回话分五类（`classify_failure`）：

| 类别 | 判据 | 动作 |
|---|---|---|
| quota | **HTTP 403 code 12001「已达每日页数上限」** | 记 `quota`，`deferred` 中止整批；额度已尽，重试与切分都没用，次日复跑即续 |
| queue-full | 10010「任务提交队列已满」、429、5xx | 退避 20/45/90/180/300 秒重试同一段，**不切分**（切小不解决排队）；退避用完记 `deferred` 并中止整批 |
| transport | 有 Traceback 且是 ConnectionError/Timeout/断连 | 同尺寸重试一次，再失败才切半 |
| fatal | 其余 401/403、Token Invalid | 直接停，记 `api-fatal`；切分与重试都没用 |
| other | 413、10003 文件过大、422 等 | 一次就切半 |
| job-failed | 平台回 `state=failed`（任务本身死了） | **先丢掉 jobId 重提一个新任务**（最多 3 次），再走切分 |

**额度用尽与队列满都是账号/平台级状态**，所以第一本 `deferred` 后 `ctx["abort"]` 让整批停下，
不再排后面的书。

> 2026-10-19 实测更正：额度用尽返回的是 **HTTP 403 code 12001**，不是 429。当天 16:23 撞上时
> `classify_failure` 把它当成了鉴权错（fatal），于是没有中止整批，而是逐本记 `api-fatal` 一路
> 空转到批末——148 本被这样误记（每个 `logs/*.json` 的 `note` 里留着原始的 403/12001 回话）。
> 已改正分类器并加离线用例 7 锁住；这 148 条是历史记录，次日复跑会被覆盖。

> 2026-10-20 实测更正二：平台会偶发把单个任务判 `state=failed`（一句「OCR服务请求失败，状态码 500」）。
> 旧逻辑见到账上有 jobId 就去续跑同一任务，而失败的 jobId 永远是 failed，于是那本书永久卡在
> `chunk-failed`（B1623《飞发》末段 5 页就是这样，且 5 页短于 `MIN_CHUNK_PAGES`，连切分都退不出来）。
> 现在 `dead_job(tail)` 认 `state=failed`，先作废 jobId 重提新任务，最多 `MAX_DEAD_JOB_RESUBMIT=3` 次，
> 离线用例 8/9 锁住。

## 验收门槛（`gate`）

必须同时满足才 `os.rename` 进 `库/<书>/md/`：逐页覆盖 1..N 无缺页、无重复页、无缺图、
`verify_output.py` 退出 0、内容文件 ≥1、正文字数 >0、可疑页 0。可疑页 = 该页 OCR 读出 0 字
且 70dpi 灰度下 ink 在 0.4%–35%、行带或列带 ≥8（口径同 `pdf_scan_probe.py`），也就是「原图有字
但一个字都没读出」。读出 1–19 字的短页（扉页、图版页）只记数不拦。过了的门槛但被受理的例外写
`overrides/<uid>.json` 的 `{"accept": "原因"}`，状态记 `accepted`，原因同时写进 `.manifest.json`
与日志。

## 2026-10-22：可疑页兜底改走 MinerU，读不出就跳过

这条路由操作人定死，以后不再为这类页人工考古、反复试。

**判据。** Paddle 的版面检没认出正文时，整页会返回空，而纸面上明明有字。这类页（`pdf_checks`
里的可疑页：OCR 0 字、ink 0.4%–35%、行/列带 ≥8）现在按两条走，不再挂 `staged-review`：

1. 把可疑页单独切片交 MinerU precision（`--model vlm --ocr`）补投一次，读到的正文写回

## 2026-10-22：额度用尽后的中断语义（在飞分片可撤销，账立即可续）

**现象。** 11:47 撞每日上限后，driver 并没有停下，还要再等 28 分钟才退出（11:47 → 12:15）。
根因是 `run_pilot()` 起的 `paddleocr_pilot.py` 子进程在轮询一个额度耗尽前就已受理的任务，轮询
上限是 pilot 自己的 `--timeout 1800`。一次超时之后，`work_chunk` 又按「账上有 jobId 就续跑」
再起一个 pilot，再等 30 分钟，三段接力。量出来的浪费：三个续跑名额一共约 90 分钟，今天实际
耗掉 28 分钟（中途人工 kill 了两次才提前结束）。

**改法（`pdf_md_batch.py`）。**

1. `run_pilot()` 把子进程登记进 `ctx["pilots"]`，退出时注销；
2. 撞 12001 的线程调 `cancel_pilots(ctx)`，宽限 `CANCEL_GRACE=60` 秒（已受理的任务可能马上就
   done，那 150 页额度已经付过，能落就落），宽限过后 `terminate()`，5 秒不退再 `kill()`；
   取消器幂等，只起一个；
3. `run_pilot()` 返回后先看 `ctx["abort"]`：已置位就把这一段记 `interrupted`、保留 jobId、
   **把 `attempts` 退回一格**，直接返回，不再进 `classify_failure`。这一步是关键，否则每次中断
   都记一次失败，连着几天撞额度就会顶到 `MAX_RESUME_ATTEMPTS=3`，之后不再续跑 jobId 而是重新
   提交同一段，白花额度。

**丢掉什么。** 只丢轮询进程本身。jobId 在收到那一刻就落账了，任务结果在平台侧，次日
`--job <jobId>` 续跑不重花额度。若被杀的是「还没拿到 jobId 的提交阶段」，服务端可能已受理而账上
没有 jobId，次日会重提一次，最多多花一段（150 页）。下载阶段被杀则 `paddle_run.json` 未写，
下次续跑会重下一次，不丢不重。

**验证。** `tests/chunk_ladder_test.py` 用例 10（在飞 pilot 宽限后被 terminate、被中断的分片记
`interrupted` 且 `attempts` 不增）与用例 11（次日带 `--job` 续跑、不重提），11 个用例全过。

**今天的真实遗留。** B0779《失落》的 `[151,300]` 分片账上是 `split`、`jobId 106595826521956352`、
`attempts 3`；下次跑批 `run_one` 会把没 done 的段重置成 `attempts=0`，按 `--job` 续跑这一段。
观察点：`logs/B0779.log` 里出现 `--job 106595826521956352` 就是续跑，不是重提。

**账与产物**（都可续跑，重跑不重花额度）

- `work/<uid>/mineru/jobs.json` 切片账：range / 切片文件 / 输出目录 / status / taskId

- `work/<uid>/mineru/out/<range>/` 每片一次 precision 任务，有 `*_content_list.json` 就算这一片完成
- `work/<uid>/mineru/rescue/{vlm,pipeline}/p%04d/` 可疑页的单页补投

1. **整片 vlm 会整页丢字。** 814 页里有 107 页（13%）被版面模型并成一个空 `code` 块，全是密集
