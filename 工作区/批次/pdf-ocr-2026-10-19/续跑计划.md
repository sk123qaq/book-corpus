## 2. 主流程：一条命令起 supervisor，跑满额度为止

```bash
cd ~/文档/books
nohup 工作区/批次/pdf-ocr-2026-10-19/wave_supervisor.sh "" 60 >> /tmp/ocr-supervisor.log 2>&1 &
```

`wave_supervisor.sh` 干的事（第一参数是「先等待的 driver pid」，空着表示立刻开跑；第二参数是
最大轮次）：

1. 前台跑驱动 `pdf_md_batch.py --batch pdf-ocr-2026-10-19 --workers 3`，输出 `/tmp/ocr-wave-runN.log`；
   驱动自己读 `defer/lang.tsv`，日文原版不排进队列；
2. 每轮结束看日志再决定：
   - 见 **`每日页数上限`**（HTTP 403 code 12001）→ 日额度用尽，**自动跑收尾并退出**；
   - 被 `10010` 队列满中止但有进展 → 等 600 秒续跑；
   - 零进展又无额度错（纯拥堵）→ 每 900 秒重试，连续 6 轮才停；
   - 范围内 369 行（411 减 42）全部有 md → 收尾退出；
3. 收尾 = `build_library.py --emit-json` → `gen_book_catalog.py` → `verify_phase.py` → `--report`，
   汇总写 `/tmp/ocr-supervisor.log`。

不看日志也可以手工分两步：

```bash
PY=工作区/.venv-pdf/bin/python
$PY 工作区/脚本/pdf_md_batch.py --batch pdf-ocr-2026-10-19 --dry-run   # 先看这次会跑谁，不花额度
nohup $PY 工作区/脚本/pdf_md_batch.py --batch pdf-ocr-2026-10-19 --workers 3 >> /tmp/ocr-wave.log 2>&1 &
# 等它自己 deferred 停下（或 Ctrl 掉）之后：
python3 工作区/脚本/build_library.py --emit-json
python3 工作区/脚本/gen_book_catalog.py
python3 工作区/脚本/verify_phase.py
$PY 工作区/脚本/pdf_md_batch.py --batch pdf-ocr-2026-10-19 --report
```

**不要在批次还在写 `库/**/md/` 时跑 `build_library.py` / `verify_phase.py`**：箱 5 的两遍重建
哈希会因中途状态变化假失败。收尾只在驱动退出后跑。

## 3. 续跑是幂等的，不会重花额度

- 每个分片的产物在 `work/<uid>/chunks/c%04d/`，有 `paddle_run.json` 就算完成，重跑直接跳过；
- 已受理但没下完的分片用账上 `jobId` 续跑同一个任务，不重新提交；
- 每次运行给每段新的 `attempts`/`queue_rounds` 预算，所以重复运行不会把上一轮的退避次数带进来；
- 目标 `库/<书>/md/` 已存在就 `skipped-has-md`（要覆盖得加 `--replace`）；
- 探页账 `defer/lang.tsv` 同样幂等：已判过的书不重探，要重探加 `--force`。
- 可疑页（Paddle 读出 0 字而纸面有字迹）自动交 MinerU 补投一次，读不出就按跳过受理，账在
  `skipped-pages.tsv`（见 `说明.md` 的「可疑页兜底」）。同一页重跑会再投一次 MinerU，所以
  不要对已落地且有 `skipped-pages.tsv` 记录的书反复重跑。

## 4. 验收判据（每本落地都要满足）

1. `python3 ~/.agents/skills/ebook-to-md/scripts/verify_output.py <md目录>` 退出 0；
2. `logs/<uid>.json` 记 `verify_rc=0`、`coverage_ok=true`、`suspect_miss_pages=0`
   （可疑页由驱动自动交 MinerU 补投；MinerU 也读不出的页记在 `skipped-pages.tsv`，状态转 `accepted`）；
3. `库/<书>/md/` 里 `README.md` + `<书名>.md` + `.manifest.json` 齐，manifest 的 `method` 是
   `paddle-ocr`、`single_file: true`。

批级别的三条同 `说明.md` 末的 Done means：`verify_phase.py` 末行「全过」、`pending_md` 继续下降、
`build_library.py --emit-json` 输出 `conflicts=0` 且 `md_done` 增加。

## 6. 出问题怎么判（对照表）

| 现象 | 含义 | 动作 |
|---|---|---|
| 日志见 `每日页数上限` / HTTP 403 code 12001 | **日额度用尽** | supervisor 自动收尾；次日同一命令再起 |
| `10010` 任务提交队列已满 | 平台拥堵，账号级 | 驱动退避 20/45/90/180/300 秒；supervisor 会隔 600 秒续跑 |
| 平台回 500 / job `state=failed` / 轮询 SSL EOF | 平台侧抖动（2026-10-20 12:44 实测过一轮） | 单页会重提即好；成片卡住就停掉重跑，已完成分片不重花额度 |
| `logs/<uid>.json` `status=staged-review` | 门槛没过。可疑页已自动走 MinerU 兜底，能落到这一步的只剩 `verify rc≠0` 这类正文缺陷 | 看 `logs/<uid>.log` 末尾的门槛行，按 `说明.md` 的可疑页流程处理；可疑页本身不用再看图，兜底读不出会自己转 `accepted` |
| `logs/<uid>.json` `status=interrupted` | 撞额度时这个分片还在飞，被 `cancel_pilots()` 收掉了；jobId 在账上，`attempts` 没增 | 不用管。下次跑批自动按 `--job <jobId>` 续跑这一段，不重花额度（观察点：`logs/<uid>.log` 里出现 `--job`） |
| `status=api-fatal` | 真鉴权/参数错（如 403 + code 10004 Token Invalid） | 查 `~/.config/PaddleOCR/api_key` |
| `status=chunk-failed` | 某段多次不成 | 看 `logs/<uid>.log` 的失败分类 |
| `status=source-changed` | 源 PDF 的 sha256 与人账不符 | 停下人工查，不要强跑 |

注意：`logs/` 里那 **148 条 `api-fatal` 是 2026-10-19 的历史误记**——那天额度用尽回的是
403/12001，旧分类器把它当鉴权错。分类器已改（`quota` 类），这些书复跑会被覆盖，`--report`
看到 `api-fatal` 148 不用慌。
