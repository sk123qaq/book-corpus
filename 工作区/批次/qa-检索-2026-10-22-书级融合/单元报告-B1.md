`BookScore` 的字段与方案一致：`book, title, type, chapters, best, best_path, best_line, best_text, support, topk, coverage, score, groups, has_prefix, has_queries`，另加四个对照方案要用的原料字段 `scores, hits, mean, total_groups`。

默认公式按方案实现：

```
best     = max(score)
support  = min(5, 段落分 >= 0.75*best 的段数)
topk     = 最好的 min(3, support) 段分数的均值
coverage = 命中的组词数 / 组词总数
score    = 0.60*best + 0.25*topk + 0.15*coverage + 0.05*log1p(support)
```

`best <= 0` 的书丢弃。并列键 `(-分, book, best_path, best_line)`。只有 `best_support_length` 含 `-0.02*log1p(chapters)`，默认方案不含。章节数读 `derived.chapters`，缺行时数 `库/<book>/md/*.md`。`has_prefix` / `has_queries` 从 `expand` 表读存在性，无行记 False。

## 性能验证

```
$ python3 .../test_book_score.py --perf
题数 60（概念表前 60 个键，按题号奇偶交错跑，端到端含搜索）
装载 meta/expand 一次性开销 143.8 ms
基线 search+rollup_by_book(mix)  p50 13.7 ms  p95 158.3 ms
本轮 search+rank(best_support)   p50 11.1 ms  p95 158.9 ms
规则 本轮 p95 <= 基线 p95 + 100 且 <= 500: PASS
2000 段聚合（10 次中位数）  基线 1.0 ms  本轮 16.7 ms
wall 5.24 s
```

规则读数：本轮 p95 158.9 ms，基线 p95 158.3 ms，差 0.6 ms，两条上限（基线+100 ms、500 ms）都远未触线。

聚合本身慢了 16.7 倍（1.0 → 16.7 ms），原因是新路径每个段落都要重算组词命中（`re.sub` 去排除词再逐个 `in` 判断），旧路径只累加已有的 `coverage`。16.7 ms 对 2000 段仍是可接受量级，但它是 B6 换默认值时要盯的一项。

装载 `meta` 与 `expand` 是一次性 143.8 ms（`expand` 表 104,293 行）。放在常驻进程里只付一次；CLI 每起一个进程付一次，这次没算进 p95。

## 发现的问题（没在 B1 改）

1. `礼治` 的第 1 名是 `乡土中国（2）`，第 2 名才是 `乡土中国`。同书两个版本都在库里，评分没区分版本，B2 的 gold 要么指定禁掉重复本，要么按书族合并。
2. `干部考核` 的目标书排第 2，第 1 名是另一本报告文学。单段落命中的书分数只差 0.07，说明 `support` 全等于 1 时排序几乎只由 `best` 决定。B2 要看 `evidence_hit@10`，不能只看书命中。
3. `韩立` 的 2000 段候选全部落在同一本书里，`hits` 字段等于 pool 上限。若 pool 提到 4000，`sum` 会继续涨而 `best_support` 只动 `mean`（默认分里没有 mean），这正是方案要的行为，但 B2 记录 `long_share@10` 时要说明 pool 是 2000。
4. `book_rank_bench.py` 原先取 400 段候选。这个 400 不是 `collect` 的 `depth`，而是 `qsearch.search` 的 `pool` 默认值，`depth` 再大也被 pool 卡住。评审后已改为 `depth` 与 `pool` 都跟 `--depth` 走，默认 2000，与前文 `qsearch --book` 同口径。`--depth 400` 可复现 2026-10-22 之前的旧读数。

## 评审后修正（2026-10-22 晚）

操作人指出 `book_rank_bench.py` 的 400 段口径不对。改动两处，都在 `book_rank_bench.py`：`collect(..., depth=2000)`，并把 `qsearch.search` 的 `pool` 也传成 `depth`。第一条改动本身不够，只改 `depth` 时输出仍是「400 段候选」，因为卡住的是 `pool`。

重跑读数（`live/B1/bench.txt` 已覆盖）：

| 概念 | 旧口径 | 新口径 | `best_support` 前 10 是否变 |
|---|---|---|---|
| 自由 | 400 段候选，161 ms | 2000 段候选，264 ms | 前 10 名次不变，第 2 到 5 名的段数从 2/2/3/5 变 4/13/15/137，分数差 0.02 以内 |
| 内卷 | 55 段（不够 400） | 55 段 | 不变 |

修正后重跑单元验证，仍 `PASS 6 cases`。五条实跑与性能探针不经过 bench，读数未受影响。
