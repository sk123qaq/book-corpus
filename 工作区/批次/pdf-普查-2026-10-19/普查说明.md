## 1. 类型分布

| 类 | 本数 | 页数 | 体积 | 判据（census 实测） |
|---|---|---|---|---|
| C 扫描件 | 468 | 144,389 | 14.68 GB | 有文本层的页 <20%，且 80% 以上页是整页图 |
| C2 无文本层且非整页图 | 12 | 3,437 | 0.50 GB | 同上但图不满页（碎片图、拼版） |
| B 文本层+图 | 47 | 12,278 | 0.93 GB | 有文本层的页 ≥50%，且有插图 |
| A 纯文本层 | 12 | 2,525 | 0.08 GB | 有文本层的页 ≥90%，每页 ≥200 字 |
| B2 局部文本层 | 1 | 121 | 0.08 GB | 有文本层的页 20%-50% |

无文本层不等于无字。扫的是纸，字在像素里。`文本层` 是 PDF 里的可选文字数据，扫描件没有。

三个反直觉的实测点，方案按它们设计：

- **字体表不能当判据。** 468 本 C 类里有一部分挂着字体（如南北朝宋体 CID 未嵌入），`pdffonts` 有行，
  但 `pdftotext` 全书只吐 20 个字。反之有书三四种嵌入字体却半页无字。只有逐页字数可信。
- **产家字段被污染。** 481 本扫描件里 261 本 producer 是 `AnnasArchive`、75 本是 `zlib`，是下游打的水印，
  不是原始扫描/OCR 软件。靠元数据认不出「已有 OCR 文本层的扫描件」，只有 2 本看着像商业 OCR（ABBYY、Acrobat）。
- **1bit 位深的扫描占 281/481 本。** 这类 CCITT/G4 二值图正是 MinerU 会静默返回空页的那批（见
  `~/.hermes/skills/productivity/mineru/references/scanned-book-qa.md`），转的时候必须带逐页体检与补页。

## 3. 三条路线

### 3.1 文本层书，本地抽（56 本，14,475 页）

用 pymupdf 抽文本，pdftotext 做交叉核对，图片按页抽进 `images/`。结构按操作人 2026-10-19
的规则分两种：**PDF 自带目录（书签）** 的按目录切章，一章一个文件；**没有目录的只生成一个
md 文件**。字号聚类推标题那一档不用了 —— 给没有目录的书编一层目录不值当，错切还会打乱锚点。

实测的难点在切分，不在抽取：

- **59 本深测里只有 16 本带书签，43 本没有。** 也就是这 56 本里大约 16 本走切章、40 本走单文件。
- **字号种类中位数 154 种**，印刷书的字号被四舍五入成一大堆近似值；这个数字现在只用来说明
  「为什么不拿字号聚类切章」。
- **乱码率可忽略**（最高 1.05%，仅 2 本 >0.1%），文本层可信度没问题。
- 这 56 本里有相当一部分是画册、攻略、设定集（Hokusai、Bayonetta、幻方、中国晋祠），图片是
  主要内容；单文件正好省掉为图册编目录的力气。

方法标记写 `pdf-text`（新值，与 `ebook-to-md`、`paddle-ocr` 区分）。

### 3.2 扫描件，OCR（411 本，138,002 页）

两条通道都已实测，主通道用 PaddleOCR-VL 云端，MinerU 降为交叉核对与补页手段。详细数字见第 6 节。

PaddleOCR-VL 用 `工作区/脚本/paddleocr_pilot.py`（token 在 `~/.config/PaddleOCR/api_key`）。
选它的依据有两条实测。一是在 MinerU 九月跑空、最终组装里 0 字的第 282、398 页上，Paddle 读出 221 与 216 字的正文。
二是在同一个 92dpi 1bit 扫描本上跑 100 页，两家的逐页字数中位数只差 9 字（Paddle 613，MinerU 622），
按 20 字窗逐字比对 400 窗命中 353（88.2%），未命中的都是异体字取舍（廩/廪、嚳/喾）而不是错读。
结构弱不再是要紧的事：扫描书按操作人的规则只出一个 md 文件，Paddle 的段落内联正好够用；
条目名没成标题只影响阅读版 html，不影响检索。

MinerU 留着做三件事：单页补投（`rescue_pages.py`）、逐页体检（`page_health.py`）、
以及 Paddle 结果可疑时的同页重读。它的 `full.md` 会丢页脚注释，凡从它出文本一律按 `*_content_list.json` 重建。

两条通道都要过同一套体检，不能因为哪家宣称完成就信：

方法标记 `mineru-ocr`（方案 §7 已定），产物进库后语料仍算低可信，`book-corpus-qa` 引用时要标注。

### 3.3 不转，只记录（73 本，10,273 页）

操作人 2026-10-19 定的规则，满足任一条就不转，只进 `skip_list.tsv` 与 `triage_final.csv`：

1. 二级学科是设定集与美术集、图册与写真、漫画与画集；
2. 图片占比超过一半（扫描件看纸面探针，文本层书看有文本层的页占比）；
3. 复核判为图片书。

图片占比过半这一条挡掉了一批复核判为「混合」的书（建筑图录、壁画集、民间美术图录，
以及带教程正文的《国际游戏场景概念艺术设计》）。它们的图注、图说、短前言是有语料的，
所以原因逐本写在 `skip_list.tsv` 的 `why` 列，想收随时能按 `route_metric` 与 `verdict` 列重开。

DB 的 `derived` 表只有 `none/partial/done/failed` 四态，没有「不适用」，这 73 本会一直留在
`v_pending_md` 里，是已知的账目噪声；`apply_jobs.py` 落地后补 `job` 行的 `skipped` 态。
人账 `目录/分类表.csv` 的备注列也应当写上「图册不转」一句，那是下一会话读得到的地方。

## 4. 输出契约

和 ebook-to-md 同形，复用它的验证器。**结构按操作人 2026-10-19 的规则分两种**，由源文件
决定，不由取字方式决定：

- **单文件（默认）**：一个内容文件 `md/<书名>.md`，页序拼接、空页跳过。所有扫描书与没有目录的
  文本层书走这条。
- **切章**：只有「纯文本层且 PDF 自带目录」的书按目录切，`NN_<章节标题>.md` 一章一个文件。

两种结构都带：

- `README.md`，与库内其余书同一套字段（`合集 / 作者 / 日期 / 章节 / 图片 / 来源`），
  `## 目录` 每行一条链接；合集、作者、日期来自人账，不知道就不写那一行（日期不能拿生成日顶替）；
- `images/`（只放被引用的图，相对路径 `images/xxx.jpg`），未引用的删；
- `.manifest.json`（uid、method、tool_version、source_sha256、pages、chapters、bytes、
  审计比值、受理例外；单文件带 `single_file: true`）。

这样 `verify_output.py` 与 `audit_volume.py` 那套门槛直接沿用，`build_library.py` 重扫
`库/**/md/` 时会按 `.manifest.json` 的 method 落 `derived` 行，不需要改 DB 写入路径。
一个 md 目录一本，`工作区/批次/<批次>/out/<uid>/` 暂存，过检后同盘 `os.rename` 进 `库/<书>/md/`。

拼装器是 `工作区/脚本/pdf_ocr_to_md.py`，`--structure single|chapters`，默认 `single`。

文本层路线（`pdf_text_to_md.py` 待写）：

2. 新写 `pdf_audit_volume.py` 做 PDF 侧对账，md 正文占源书文本层字数 ≥95%，并给逐页锚点覆盖率

3. 带目录的书抽读最小与最大两个章节文件，确认标题是标题、图片能开。

OCR 路线（已写成 `pdf_md_batch.py` 的 `gate`，实录见 `pdf-ocr-2026-10-19/说明.md`）：

1. 合并后的逐页账 `per_page` 页号恰好是 1..N，不重不缺；每个分片的 `per_page` 与其 range 逐页对齐；
2. `verify_output.py` 退出 0；内容文件 ≥1、正文字数 >0；
3. 逐页体检：OCR 读出 **0 字**而纸面上有字迹结构（70dpi 灰度 ink 0.4%–35%、行/列带 ≥8，
   口径同 `pdf_scan_probe.py`）的页算可疑页，不为 0 则不落地，原图存 `review/<uid>/` 给人看；
   读出 1–19 字的短页（篇章扉页、图版页）只记数，不拦 —— B1583 曾因此被误拦 4 页，
   渲染后确认那些页的标题（`## 灵视的世界` 等）已经读出来了；
4. 每个分片的 jobId、页数、字数都在账上（`work/<uid>/chunks.json` 与 `logs/<uid>.json`）；
5. 已查清原因的例外写 `overrides/<uid>.json` 的 `{"accept": "原因"}`，原因同时进 manifest 与日志。

MinerU 的 `page_health.py`/`rescue_pages.py` 不再进入主流程，只当 Paddle 结果可疑时的人工手段；
它们的 `content_list` page_idx 口径不适用于 Paddle 的输出。

## 6. 成本与产能

两条 OCR 通道的实测对比（数字都在 `paddle_runs.jsonl`）：

| 项 | PaddleOCR-VL 云端 | MinerU 精度接口 |
|---|---|---|
| 单次任务页数 | 实测 105 页全解析，官方建议 ≤100 | 硬上限 200 页 |
| 解析速度 | API 端 0.42-0.98 秒/页（311 页合计 304 秒） | 234 秒落定 7/8 切片，合 6 页/秒 |
| 日额度 | 平台页面写 20000 页/天；2026-10-19 实测撞上后接口回 **HTTP 403 code 12001「已达每日页数上限」** | 1000 页/天最高优先，超出降级 |
| 静默丢页 | 本次 311 页未见丢页 | 1bit 扫描上实测 3%（1509 页里 44 页），要补投 |
| 段落结构 | 弱，条目名常内联 | 强，大词典有 73 个 H1 / 790 个 H2 |
| 上传 | 本机实测 0.11-0.74 MB/s，大文件会断 | 未测 |

按 Paddle 通道算，138,002 页 API 端约 37.6 小时计算量（按 0.98 秒/页），分片并行后可压缩。
真正的瓶颈是额度，20000 页/天的话排期 **6.9 天**。上传是新增的瓶颈，14.7 GB 按 0.3-0.7 MB/s 要
6-14 小时，脚本带 `--job` 续跑，失败不重花额度。

2026-10-19 11:15 到 11:57 的一次试跑把两个新上限量出来了：

- **提交接口会长时间拥堵。** 35 次提交（含三次 2 页小探针，跨度 42 分钟）全部回
  `HTTP 400 code 10010 任务提交队列已满，请稍后重试`，一次 jobId 都没拿到，额度零消耗。
  10010 在官方错误码表里是可重试类，所以应对是**退避重试同一段，不切分**（切小不解决排队）。
  队列满是账号/平台级的，处理见 `pdf-ocr-2026-10-19/说明.md`。

  **额度用尽的回话是 HTTP 403 code 12001「已达每日页数上限」，不是 429**（2026-10-19 16:23 实测）。
  当天驱动把它当成了鉴权错（fatal），没中止整批而是逐本记 `api-fatal`，148 本被误记；分类器已改，
  额度现在单独一类 `quota` → `deferred` + 中止整批，离线用例 7 锁住。
- **分片从 30 MB 压到 15 MB。** 29.9 MB 的切片第一次上传就 180 秒超时（判为传输类），
  而 11.8 MB、14.2 MB 能拿到干净回话；官方上限是本地文件 50 MB，15 MB 留了三倍余量。

这两条在 2026-10-19 下午的试跑里全用上了：B1583《路上的祖先》255 页分成 67+67+67+54 四段，
第 2 段退了 3 次（20/45/90 秒）才提交上，第 4 段先退 5 次被拒、下一轮再退 4 次才受理；
已受理的三段在重跑时直接跳过，没重花额度。**拥堵时段的 API 端吞吐是 4.3 秒/页**
（54 页 231.8 秒），比早晨实测的 0.98 秒/页慢四倍，所以真实排期会随平台负载浮动，
不能拿早晨的数字当承诺。

本地 GPU 仍然顶不上。TeleOCR 在这台 RX 9070 上约 105 秒一页（引自 `~/teleocr/LOCAL_SETUP.md` 的历史实测），
143k 页要 166 天 GPU 不停，只适合点状补疑难页。

磁盘不是瓶颈。`/home` 剩 255 GB。按已入库 3 本 OCR 产物估，md 正文 1.5-7 KB/页，143k 页约 0.2-1 GB。
