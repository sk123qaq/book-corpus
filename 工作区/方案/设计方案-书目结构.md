## 1. 三条账，一个字段一个写入者

现在的问题是同一本「书」的信息散在四五个地方，谁都能写，所以对不上。改成三条账，各管各的。

| 账 | 位置 | 谁写 | 内容 | 丢了会怎样 |
|---|---|---|---|---|
| 人账 | `目录/分类表.csv` | 你（或我按你的指令改） | uid、一级、二级、作者层、保留、正式书名、备注。1392 行 | 分类信息要重填，书和正文不丢 |
| 机账 | `工作区/批次/<批次>/jobs.jsonl` 与 `decisions.tsv` | 每次下载或转换追加一行，一个演员一个文件 | 每一次尝试的输入、结果、错误、证据路径 | 无法判断哪本跑过、为什么失败 |
| 产物 | `目录/library.db`、每本 `book.json`、`目录/*.md` | 脚本生成 | 由人账加机账加磁盘扫描推出来的索引 | 重跑一次即可，秒级 |

规则是死的：

- 人只改人账。不要在 `library.db` 里 UPDATE，不要在 `book.json` 里手改字段，改完会被下一次生成覆盖。
- 脚本只写产物。脚本读人账、机账和磁盘，写 DB 与 `book.json`。
- 并发演员不共享写目标。子代理各写各的 `jobs/<演员>.jsonl`（一个演员一个文件），最后由一个汇总脚本导入 DB。这样并行跑 10 个子代理也不会互相锁库。
- 全量重建比增量写入便宜。实测索引构建 0.33 秒，所以每次新增书都整库重建，不去写复杂的增量逻辑。

三处路径决策，理由都是省事：

- `md/` 里放 ebook-to-md 的原样产物。章节文件互相引用 `images/xxx.jpg`，整目录搬过去相对路径不用改。

## 4. 命名、uid、路径派生

- `uid` 形如 `B0731`，由 `ingest.py` 分配一次，此后不变。人读、引用、写笔记都用它。
- 身份判同用 `source.sha256`。换源、改名、移动之后，脚本按 hash 认回同一本，uid 不变。
- 路径由分类表派生，是投影不是事实。`库/<一级>/<二级>/<作者层?>/<书名>/`。
- 作者层只在同一作者集齐 3 本以上时建。实测会触发的是阿加莎 85、东野圭吾 69、余华 13、王小波 10、吉姆·柯林斯 4、杰克·韦尔奇 3。
- 书名清洗规则沿用现有 `gen_book_catalog.py` 里那套：去作者括注、去 z-library 后缀、去截断省略号，上限 60 字符。清洗后的名字只做目录名，原名留在 `book.json`。
- 同名冲突分两种处理。`sha256` 相同的是同一本的多份源，合并成一本，两个文件都进 `source/`。`sha256` 不同的是两本书，书名加限定词。本次实测 12 处冲突，是人账里要拍板的清单。

## 6. library.db

### 6.1 表

```sql
CREATE TABLE book(
  uid TEXT PRIMARY KEY, title TEXT, title_from_file TEXT,
  author TEXT, translator TEXT, publisher TEXT, language TEXT,
  subject1 TEXT NOT NULL, subject2 TEXT,          -- 一级必填，二级可空
  path TEXT NOT NULL,                             -- 相对 库/ 的路径
  path_state TEXT NOT NULL DEFAULT 'proposed'
    CHECK (path_state IN ('proposed','active')),
  retention TEXT NOT NULL DEFAULT 'keep'
    CHECK (retention IN ('keep','review','drop')),
  notes TEXT);
-- 规划期允许同名占同一个路径，落地期不允许两本书实际住同一个目录
CREATE UNIQUE INDEX book_active_path ON book(path) WHERE path_state='active';
CREATE TABLE source(
  uid TEXT NOT NULL, file TEXT, format TEXT, bytes INT, sha256 TEXT,
  origin TEXT, batch TEXT, sha256_ok INT);
CREATE TABLE award(name TEXT PRIMARY KEY, org TEXT);
CREATE TABLE book_award(uid TEXT, award TEXT, year TEXT, edition TEXT, result TEXT);
CREATE TABLE derived(
  uid TEXT, kind TEXT CHECK (kind IN ('md','html','ocr')), status TEXT,
  method TEXT, tool_version TEXT, source_sha256 TEXT, chapters INT, bytes INT,
  generated_at TEXT, manifest TEXT,
  PRIMARY KEY (uid, kind));
CREATE TABLE job(
  job_id INTEGER PRIMARY KEY, uid TEXT, kind TEXT, status TEXT
    CHECK (status IN ('pending','running','done','failed','skipped')),
  attempt INT, actor TEXT, batch TEXT, source_sha256 TEXT,
  tool TEXT, tool_version TEXT, started_at TEXT, finished_at TEXT,
  error_code TEXT, error TEXT, output_path TEXT, evidence TEXT,
  UNIQUE (uid, kind, batch, actor, attempt));   -- 同一演员重试同一本书要能追加，不能被唯一键挡住
```

视图（代替手写查询脚本）：`v_pending_md`、`v_coverage`、`v_award_book`、`v_dup_sha`、`v_series_volume`、`v_path_conflict`。

L1 只建上面六张表。章节级的 `chapter` 表留到转换阶段再建，现在没有数据可填，见 7 节。

章节正文不进库。库里只存章节的路径、标题、字节数、hash，正文留在 md 文件里。34,761 个章节文件的元数据是几 MB，全文索引是另一个量级，理由在 6.3。

### 6.2 读写纪律

- 只有 `build_library.py`（整库重建）和 `apply_jobs.py`（把机账导进 job 表）写库。
- 查询走 `工作区/脚本/lq.py`，它用只读 URI 打开。临时 SQL 用 `python3 -m sqlite3 目录/library.db "SELECT ..."`，本机没装 sqlite3 命令行，Python 自带的这个能跑（实测 SQLite 3.51.2，FTS5 可用）。
- 开 WAL，单写者。人账与机账是文本，可以进 git，`库/**/source`、`库/**/md`、`库/**/html` 与 `工作区/中间态`、`工作区/废弃` 进 `.gitignore`。

### 6.3 全文索引先不做

实测对比（数字与命令在附录 A）。3000 个章节文件、50.4 MB 正文上，FTS5 加 trigram 分词建一次 20.0 秒、占 178 MB（正文的 3.72 倍）、查询 0.26 毫秒；rg 扫同一批 35 毫秒，扫全库 34,761 个文件 0.09 到 0.53 秒。

全库正文 451.6 MB，按同一比例外推，FTS 索引约 1.7 GB、建一次约 3 分钟。外推的假设是耗时随正文量线性增长，限速环节是分词与写入的 CPU，实测 20.0 秒里有 18.3 秒是用户态 CPU，这个假设站得住。

结论是不划算。人问一个问题，0.26 毫秒和 100 毫秒都感觉不到，而 1.7 GB 的索引要随每次转换维护。中文检索还必须用 trigram 分词，默认分词会把一个汉字串当成一个巨大 token，查不到东西。

触发条件写在这里，等它真的出现再做：需要跨书打分排序、需要命中的上下文片段、或者要把查询嵌进一个毫秒级循环里。

## 7. 后置阶段的转换队列（本方案只定接口）

L5 之后要做的转换，范围已实测。缺 md 的 1209 本，按格式拆是 epub 628、pdf 541、azw3 21、mobi 11、txt 5、djvu 2、azw 1，合计 1209。电子书走 ebook-to-md，PDF 多半是扫描件，要先判文本层再决定是否 OCR。

数据模型就三件东西：

1. `job` 表加 `jobs.jsonl`。每行一次尝试，幂等键是 `(uid, kind, batch, actor, attempt)`，导入用 `INSERT OR IGNORE`，重跑不会重复计数。转换阶段再加 `chapter` 表（uid、序号、标题、路径、字节数、hash），章节正文仍然留在文件里。
2. 每本书的 `md/.manifest.json`，记源文件 sha256、工具名与版本、章节清单、生成时间。判据是源 hash 与工具版本都没变就跳过，变了就重跑。
3. 安装分两步。产物先落 `工作区/批次/<批次>/out/<uid>/`，跑 `verify_output.py` 与 `audit_volume.py`，再同盘 rename 进 `库/…/md/`。rename 是原子的，中断不会留半本书。

新增与插入的三条规则，避免以后越跑越乱：

- 新书进 `_收件箱/<日期>/`，`ingest.py` 分配 uid、算 sha256、往人账追一行，`build_library.py` 整库重建（0.33 秒）。不做增量写库。
- 已有书换到更好的副本，uid 不变，`source` 加一行，`derived.md.source_sha256` 对不上新 hash，`v_pending_md` 自动把这本书列回待转换。
- PDF 的 OCR 产物标 `method` 为 `mineru-ocr`，与 ebook-to-md 的产物分开。`原书pdf/md/` 里现有 3 本是 OCR 结果，迁移时就按这个标记走，否则低可信文本会混进语料库。

## 8. 迁移阶段

每阶段一个门槛，过不了不进下一阶段。回滚面有两层，rename 类操作靠 L0 的硬链接快照，改写类操作靠 L4 开工前的原件复制。

### L0 冻结与快照

- 停掉下载与转换，记下当时的 `find -type f | wc -l`，本次实测是 47,916。门槛拿这个记录值比，不要在脚本里写死常数。
- 建快照 `cp -al ~/文档/books ~/文档/books.snapshot-2026-10-19`。同盘硬链接，实测 45,633 个文件、1.3 GB 用 0.805 秒、额外占 0 块；全库 47,916 个文件里的 95% 已在这批实测里，其余按同一速率外推约 1 秒。门槛是两边文件数相等。
- 建 `库/ 目录/ 工作区/` 三个空壳，本方案与决策记录移进 `工作区/方案/`。树内移动不改变文件总数，所以门槛仍在移动之后、搬迁之前跑一次即可。
- 约束。搬迁期只允许 rename 与新建文件。禁止 `>` 截断式原地写，禁止编辑器的原地保存。GNU `sed -i` 写新文件再改名，硬链接会断开，快照安全。
- 边界。硬链接快照只防搬错与删错，不防磁盘故障，也不替代异地备份。

### L3 搬迁

- `migrate_layout.py --plan` 输出 `目录/搬迁计划.csv`，1392 行旧路径到新路径，含 1015 个奖项书文件、491 个 md 目录、2 本 html 的去向。人工过一遍。
- `--apply` 执行。只做同盘 rename，每本书建目录，`source/`、`md/`、`html/` 归位，写 `book.json`。1015 个扁平奖项文件同时变成一本一目录。
- 硬规则。目标路径已存在就中止，不覆盖。同名且 sha256 相同的两份源是同一本的重复件，保留一份进 `source/`，另一份记进 `重复.csv` 后移入 `工作区/废弃/duplicates/`。
- 门槛。四项，缺一不算过。一，`find -printf '%i %s %f\n'` 出的源文件清单迁移前后逐行一致，rename 不改 inode，这条能抓出丢文件与错配；二，每个 md 目录的章节数与迁移前一致；三，随机 20 本 sha256 与迁移前一致；四，重建 DB 后 `path_state='active'` 的行数等于 1694，`v_path_conflict` 为 0。
- 反跑。搬迁计划是双向表，`--apply --reverse` 按新路径回旧路径。这是除硬链接快照之外的第二道回滚。

## 10. 风险与未决

| 风险 | 影响 | 处理 |
|---|---|---|
| 12 处同名冲突里有些是同一本书的两份源 | 误当两本，书库里出现重复 | L2 按 sha256 判，同 hash 合并 |
| 二级分类判断反复 | 搬完还想改目录名 | 改人账加 `--move-only` 批量改名，脚本化，不手工 |

| 3 本 MinerU OCR 产物被当成拆章 md | 语料库混入低可信文本 | 迁移时标 `method=mineru-ocr` |
| 168 本待归类一直没定 | 堆在 `其他/待归类` | 可接受，`v_` 视图列出，不影响其他书 |
| 中文文件名超长或已被截断 | rename 失败，或书名不完整 | 清洗后的目录名上限 60 字符；字节长超 200 的 28 个文件名在 L1 列出来，书名在 L2 补全 |
| 只有本机一份数据，无异地备份 | 磁盘故障丢 22 GB | 本方案不解决。硬链接快照防搬错，不防硬件。要真备份就另接一块盘 |
| 人账丢了 | uid 与分类要重排 | uid 由 `ingest.py` 写进人账后不再重算。人账与机账进 git，或复制到第二处 |

未决，需要你拍板：

1. 12 处同名冲突的具体判定，L2 时我会逐条给你，你只需说合并还是改名。
2. `目录/` 与 `工作区/` 是否进 git 做版本历史。我建议进，文本量小，且人账是 uid 的唯一载体。
3. 要不要另接一块盘做真备份。本方案只保证结构信息不丢，不保证抗磁盘故障。
