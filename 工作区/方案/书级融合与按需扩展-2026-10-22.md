这份方案把书级检索从 `0.7*best + 0.3*mean` 改成 best 加 capped support。先解决两个问题，长书因为章多占位，单章书被全书平均分拉低。书级只负责捞书，章级再读 `md/README.md` 选章，`expand` 改成按需生成，不再全库铺 queries。方案分六个本地单元 B1 到 B6，每个单元都有可复跑的读数。当前只写方案，不改代码。

## 怎么读这份方案

一个勾选项就是一个工作单元。每个勾选项都要有证据，文件、日志、TSV 读数或命令输出都算。嵌套的勾选项是上一项的细步。正文是操作步骤，附录放现状、替代方案和风险。

这是本地只读方案。项目没有 git 仓库，没有 PR，没有 UI。单元开始时的工作区就是这一轮的版本。实跑证据是 CLI 输出和保存下来的 TSV 或 JSON，不是截图。PR 的十条 lane 和截图规则不适用。每个单元做三到七次实跑检查。操作人读完单元报告，再决定是否进入下一个单元。

只跑单测不算验证。一个单元只有在单元验证、实跑验证、性能验证都通过后，才算完成。在这份本地方案里，把“PR”读成“单元”，把“合并”读成“本地验收”。

执行时，代码单元用 `playbooks/feature.md`，评测单元用 `playbooks/eval.md`。不使用 autopilot 或 PR playbook，因为没有远端仓库，也没有合并队列。

这份是中文工作版。英文检查脚本只认英文骨架，所以不再用它做格式门槛。内容门槛仍然是 B1 到 B6 的读数。

## B1 书级打分核心

**依赖。** B0 基线和索引缺口决定。

**文件。**

**实现。**

- [ ] 定义 `BookScore` 记录。字段有 `book`、`title`、`type`、`chapters`、`best`、`best_path`、`best_line`、`best_text`、`support`、`topk`、`coverage`、`score`、`groups`、`has_prefix`、`has_queries`。
- [ ] 把段落命中按书聚合。分数从高到低排序。`best`、`support`、`topk`、`coverage` 都从命中段落算，不从全书所有章算。
- [ ] 默认公式如下。
  ```
  best = max(score)
  support = min(5, count(score >= 0.75 * best))
  topk = mean(top min(3, support) scores)
  coverage = distinct_groups_hit / max(1, total_groups)
  score = 0.60 * best + 0.25 * topk + 0.15 * coverage + 0.05 * log1p(support)
  ```
- [ ] `best <= 0` 的书直接丢掉。零分命中不算证据。
- [ ] 加一个只用于对照的长度项，默认关闭。
  ```
  score = score - 0.02 * log1p(chapters)
  ```
- [ ] 章节数从 `目录/library.db` 的 `derived.chapters` 读。没有这一行时，数 `md/*.md` 文件。不加表，不加列。
- [ ] 并列时按书路径、最佳段路径、行号依次排序，保证可复现。
- [ ] 加 `--explain` 输出，把每个分项都打出来，方便复查一本书为什么排在这里。
- [ ] 在 `book_rank_bench.py` 里加这些方案，`sum`、`mean`、`best`、`mix`、`best_support`、`best_top3_support`、`rrf5`、`best_support_length`。
- [ ] B1 不改 `qsearch.py --book` 的默认行为。新模块先做实验面，生产默认值到 B6 再决定。

**你会看到。**

- [ ] 一本只有一章的书，`best=1.0` 时 `support=1`、`topk=1.0`，不会被平均分稀释。
- [ ] 一本 1,000 章的书只有一章很强、其他章很弱时，`support=1`，最佳章分和单章书一样，不因为章多被拉低。
- [ ] 一本有五章都很强的书，`support=5`，只加封顶后的小 bonus，不随章数线性增长。
- [ ] 没有命中的查询返回空列表，不返回零分书。

- [ ] `test_book_score.py` 覆盖单章、长书单强章、长书多强章、无命中、并列、缺少 `derived` 六种情况。运行 `python3 工作区/批次/qa-检索-2026-10-22-书级融合/test_book_score.py`。

**实现。**

- [ ] 读候选路径已有的 `expand` 行，记录 `has_prefix` 和 `has_queries`。没有行不能当零分。
- [ ] 停止全库 `queries` 扩展。本方案不运行 `build_expand.py --kind queries --all`。
- [ ] 只对选中的书和章做按需扩展。
  - 书级分最高的 3 本，或用户选中的书，从 B3 返回的按检索分排序的章节里取第 1 章。不是书开头的前 1 章。相关章可能在 800 章之后，开头章不能代替。
  - 默认 3 本书乘 1 章，也就是 3 次模型调用。
  - `--deep` 按检索分取每本前 2 章，3 本乘 2 章，6 次调用。
  - `--max` 或用户明确要求深挖时，才允许按检索分取 8 本书乘 3 章，最多 24 次调用。24 是硬上限，不是默认值。
  - 提供方用 `opencode`，本批不用 `commandcode`。
- [ ] 按渐进披露原则把章节交给模型，不把整章直接丢过去。
  - 不固定取前 xx 行。窗口以最佳命中行为中心。最佳命中在开头时，窗口自然就是前 xx 行。最佳命中在 800 章附近时，窗口就在 800 章附近。
  - 先给元数据，再给窗口，模型需要时再请求更多。不要让模型在没有行号和字数的情况下猜整章内容。
  - 全文只在章节不超过 20,000 字，并且当前档位允许时给。超过 20,000 字的长章只给窗口或 grep 结果，不给全文。
  - 所有摘要必须带 `evidence_lines`。引用行必须落在已经给过的窗口里，落不进去就丢弃或要求模型再请求。
- [ ] 定义 `ChapterPacket` 记录。字段有 `path`、`title`、`chars`、`lines`、`best_line`、`window_start`、`window_end`、`window_text`、`level`、`has_before`、`has_after`、`readme_status`。
- [ ] 定义五层披露。
  - L0 元数据。给路径、章名、总字数、总行数、最佳命中行、前后各 200 字片段。不给正文。用来让模型判断值不值得继续读。
  - L1 默认窗口。以最佳命中行为中心，前后各 20 行，最多 2,000 字。章节本身少于 2,000 字时，直接给整章。
  - L2 深挖窗口。以最佳命中行为中心，前后各 60 行，最多 6,000 字。窗口碰到章节标题或小节边界时，把标题带上。
  - L3 定向读取。模型可以请求一个行范围，或者给出 grep 词。脚本在本地跑 grep，最多返回 10 个命中，每个命中前后 5 行，总字数不超过 4,000 字。适合长章里只关心一个概念的情况。
  - L4 全文。只有章节不超过 20,000 字，并且当前档位允许时才给。超过 20,000 字一律拒绝，要求模型改用 L2 或 L3。
- [ ] 定义模型协议。第一次调用给 L1 包和任务说明，要求模型输出严格 JSON。
  ```
  {
    "need_more": false,
    "summary": "本章与问题相关的一段话，30 到 120 字",
    "evidence_lines": [88, 92],
    "queries": ["检索式 1", "检索式 2", "检索式 3"]
  }
  ```
  需要更多内容时输出下面三种之一。
  ```
  {"need_more": true, "reason": "窗口没有覆盖定义", "request": {"type": "lines", "start": 60, "end": 140}}
  {"need_more": true, "reason": "需要找另一个概念", "request": {"type": "grep", "terms": ["支配", "强制"], "context": 5}}
  {"need_more": true, "reason": "整章很短，需要看全", "request": {"type": "full"}}
  ```
- [ ] 校验模型请求。行范围必须在 1 到总行数之间。grep 词不能为空。`full` 只有在章节不超过 20,000 字且档位允许时才执行。越界、空词、超预算的请求直接拒绝，返回 `partial` 和原因。
- [ ] 校验模型输出。摘要不能为空，`evidence_lines` 必须落在已经给过的窗口里，三条检索式必须编号且每条至少两个正文外词。不合格就丢弃，不写缓存。
- [ ] 档位与调用预算。
  - 默认档只允许 L1，3 本书乘 1 章，3 次调用，并发 3，总预算 8 秒。
  - `--deep` 允许 L1 到 L2 或 L3，最多两轮，3 本书乘 2 章，最多 6 次调用，并发 4，总预算 15 秒。
  - `--max` 允许 L1 到 L4，最多三轮，8 本书乘 3 章，最多 24 次调用，并发 6，总预算 25 秒。
  - 单次调用超时 8 秒。超时或失败跳过该章，返回已有结果，标记 `expand_status=partial`。
- [ ] 默认档收到 `need_more` 时不再追加，直接返回 `partial` 和原因。只有 `--deep` 或 `--max` 才执行追加请求。

- [ ] 每次结果写 `目录/检索/expand_cache/`。键是 `sha1(path + kind + level + window_hash + prompt_hash + mtime)`。章节 mtime 变了，对应缓存失效。不同窗口的摘要分开缓存，不能拿 L1 的摘要冒充 L2。
- [ ] 缓存命中直接跳过模型调用。重复查询应该零调用。
- [ ] 书级简介先用 README 的简介。README 没有简介时才生成。
- [ ] 长网文默认跳过生成摘要，用 README 章名和原文。社科书可以按需生成。
- [ ] 记录每次查询的 token 数、输入字符数、调用次数、轮数、缓存命中和缓存未命中。

- [ ] 深挖档或最大档里，模型说 `need_more` 时，第二轮只补它请求的行范围或 grep 结果。默认档收到 `need_more` 直接返回 partial。

**查询速度怎么保证。**

24 次串行模型调用会明显拖慢查询，所以不能把它放在首轮。默认策略是四层。

1. 首轮零模型调用，书级分、README、原文段落在 2 秒内返回。
2. 默认第二轮只扩 3 本书乘 1 章，每章只给 L1，3 次调用，并发 3，目标 8 秒内返回。只扩最佳章，够用来确认书内有没有答案。
3. `--deep` 扩 3 本书乘 2 章，允许每章多一轮 L2 或 L3，最多 6 次调用，并发 4，目标 15 秒内返回。用在最佳章不够、需要看相邻章的时候。
4. `--max` 或用户明确要求深挖时才扩 8 本书乘 3 章，最多 24 次调用，并发 6，目标 25 秒内返回。24 次是硬上限，不是日常路径。

渐进披露本身也省时间。L1 只有 2,000 字左右，比整章几万字小一个数量级。模型读得少，回得快。只有它明确说不够时才加第二轮，不主动把所有章都扩成全文。

还可以再省调用。一次调用可以让模型给同一本书的两三章各写一句摘要，输出严格 JSON。这样深挖的 6 次可以压到 2 到 3 次。默认先按一章一调，保证质量。如果 B4 实测延迟太高，再开批量模式。

### 数据流

```
问题
  -> 章级命中（qsearch_plan 或 qsearch）
  -> book_score 聚合（best + capped support + coverage）
  -> 书级 top N
  -> README 选章（B3）
  -> 选中章原文与 grep 证据
  -> 可选按需 expand（B4）
  -> 可选书卡（B5）
```

书级分不读全书每一章。它读段落命中和章节数。选中书和章之后才读 md。

### 索引鲜度门槛

B0 记录 md 书数和索引书数的缺口。B2 只用已索引目标。长书或短书目标没进索引时，换一本。如果整个 pilot 都需要一本没索引的书，在 B2 前用 `build_para_index.py --rebuild` 重建一次，记录时间和体积，然后跑 `check_p1.py`。不要在评测中途重建。

### expand 策略

停止全库 queries 扩展。当前证据不支持 84,000 章全跑。prefix 只在存在时作为可选特征。按需摘要只对书级检索后的 top 书和章生成。缓存放 `index.db` 外，坏摘要不会污染全局索引。

按需扩展不整章投喂。先给 L0 元数据，再给最佳命中附近的 L1 窗口。模型需要更多时，才补 L2 窗口、L3 行范围或 grep 结果。L4 全文只给 20,000 字以内的短章，并且只在深挖档位允许时给。摘要必须带 `evidence_lines`，引用行必须在已给窗口内。

长网文优先用 README 章名。生成章摘要对情节问题帮助小，成本高。社科书可以按需生成一句摘要。类型是策略，不是硬过滤。

### README 策略

README 是章节目录和书的简介，不是正文。用它排章节顺序、显示标题、挑候选章。用段落索引打分。用 md 正文引用。README 缺失时用文件名，并标记 `missing`。

### md 正文策略

段落索引是打分面，md 文件是证据面。不要为了给一本 1,000 章的长书排序去扫 1,000 个章节文件。只读选中的最多 3 章和引用行，默认扩展只读最佳 1 章。长书路径才会快，单章路径才会准。

## 附录 C. 被否掉的方案

**全库 queries 扩展。** 按实测单价约 60 美元，60 题证据没有显示章级收益。按 gap 选章仍有 21,296 章，还会漏硬例。B4 改成按需扩展。

**sum 或 mean 书级分。** sum 偏长书，mean 稀释单强章。现有 `mix` 比两者好，但仍然对匹配段数敏感。B1 用 capped support 替掉 mean。

**硬类型过滤。** 直接排除网文会删掉情节、人物类问题的正确答案。B5 显示类型，让用户在当前查询里排除。

**用 LLM 判书相关。** 每次查询都加成本和方差。书卡在歧义场景更便宜，还能拿到真实标签。LLM 可以以后做离线标注，不做默认路径。

**现在就上学习排序。** 还没有书级标签。B2 和 B5 才产出第一批标签。至少积累 200 条选择记录后，再考虑小 pairwise 排序器。

**新建 `book_score` 表。** 分数依赖查询，表会很快过期。从段落命中在内存里算。只有 B2 证明延迟有问题，才加缓存。

**为了书级打分重建索引。** 现有索引已经有段落和章节字段。重建是数据鲜度任务，不是本方案的一部分。

| 用户反馈只代表一个人 | 全局权重被个人偏好带偏 | 只做会话内重排。全局学习要等 200 条以上并单独评审 |
| 按需 expand 成本失控 | 一次查询调用几十次模型 | 默认 3 次，深挖 6 次，硬上限 24 次。缓存命中不计费。超过预算直接停 |
